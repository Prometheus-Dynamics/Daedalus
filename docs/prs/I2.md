## Build

- budgets.toml is the one table of budgets. Each row has: name, the measure, the tool that measures it in CI, the value on dev measured the same way, the limit, and the board_run id if a timing is also needed. The design's budget table is copied into the README with a column saying where each row is checked.
- Instruction counts use valgrind's callgrind (Ir) on a release build, run under the harness in testing/crates/budget-harness. Counts do not depend on host load, so they run on GitHub-hosted runners. perf stat counters are not used in CI.
- Dev's numbers were measured with perf stat instructions:u, not callgrind. This PR re-measures the dev baseline with callgrind on the same benchmark (idle_tick 16 stages; the stable-ABI node tick; the detector mirror graph) and records both values in budgets.toml. The limit is the callgrind value, not the perf value. The design's 27,064 is kept as a reference column only.
- Allocation counts use a counting global allocator, enabled by a test-only feature in the harness. A steady-state tick of a fused graph, a stable-ABI node and a graph passing a large handle must count zero allocations. Planning is not counted.
- Flash and RAM come from ELF section sizes on the thumbv7em and thumbv6m targets, with the convention from dev's scripts/ci.sh mcu step: flash is .vector_table + .text + .rodata + .data, static RAM is .data + .bss + .uninit. The five-node firmware row checks the design's ranges (3 to 12 KiB flash, 112 to 584 B RAM) per mode.
- GPU submit counts: an 8-op region must issue one queue submit when merged and one submit per op when not, counted with a wrapper around the queue on lavapipe. Timings are not measured in CI.
- Per-stage nanoseconds, the detector's microseconds per frame, and the GPU timings are not CI rows. They go in board_run. The bench workflow keeps the criterion comparison against the previous baseline commit, as on dev, and it is non-blocking for timings.
- crates/bench-counters is not carried. Its perf-counter reader is a board-only tool, and any board run that needs counters uses scripts/board.sh.
- A row that gets worse than its limit fails the gate, unless the PR changes the limit in budgets.toml with a reason in the commit message.
- Settled: the RX 6800 XT rows are run by a local session on the desktop, and recorded like any other board run.

## Proof

scripts/ci.sh budgets runs in GitHub CI and fails on a row above its limit. Planted regression: a fixture with one heap allocation per steady-state tick fails the allocation row. A second fixture with one extra op fails the instruction row. The flash and RAM rows pass on the thumbv7em and thumbv6m builds of the MCU firmware from D5. The GPU submit row passes on lavapipe.

## Board run

On CM5, record the per-stage overhead unfused (dev 655 ns) and fused (dev 498 ns), and the 16-stage idle tick wall time. On the detector board, record the mirror graph at about 7 µs per frame. On the RX 6800 XT, record the 8-op GPU region at 0.37 ms with 8 submits and 0.15 ms with 1. On V3D, record 1.30 ms with 8 submits and 1.32 ms with 1. ## Status

Done for the counted budgets. `scripts/ci.sh budgets` measures the rows of `testing/budgets/budgets.toml` and fails on one above its limit. The board run is in `testing/board-runs/I2.md`, untested.

**Two rows are worse than dev, and the limits hold them where they are.** A steady-state tick allocates once for every CPU node output that is not plain data of 16 bytes or less: the output is published in a new `Arc` each tick. The detector-shaped graph allocates 6 times a frame (dev: 0), and a graph whose node takes a large value and hands it on allocates once a tick (dev: 0). The design's "steady-state running allocates nothing" is not met for such outputs. The three rows the brief names are zero: a fused graph, a plugin node, and a large handle read by its consumers.

Differences from the brief:

- **Instruction rows have two checks.** The limit is dev's callgrind value, as the brief says. This branch is far under it, so a row also fails when it is more than 10% above what this branch measured when the row was set (`next`, `tolerance_percent`).
- **The gate runs `budgets` on every PR, without valgrind on the hosted runner.** There the instruction rows are reported as not run, and the allocation and firmware rows are checked. `.github/workflows/bench.yml` (the workflow `Budgets`) installs valgrind and sets `BUDGETS_REQUIRE_ALL=1`, which makes a row that cannot be run a failure. `ci.yml` is not edited.
- **The stable-ABI node row** is a plugin node's whole tick (feed, tick, take) on both branches, since that is what can be run the same way on each. Dev's 3,100 was the node alone under perf. Under callgrind the whole tick was 14,425 on the stable path and 10,655 with the node installed statically.
- **The dev stable-path baseline needed a scratch test.** The case had no entry point that runs one path a given number of times, so a short test was added in a scratch checkout of dev. Dev is unchanged. `testing/budgets/README.md` records how each baseline was taken.
- **The detector graph is rebuilt, not ported.** `testing/crates/budget-harness/src/detector.rs` has dev's shape (five stages, the input fanned out to four, constants on each, state on two, struct outputs) with constant inputs in place of config structs.
- **The planted instruction regression** is checked against a limit set to what the plain chain costs in the same run. The extra operation is 5 `Ir`, far inside the gap to dev's limit.
- **The GPU submit row is not run by `budgets`.** E12 counts it on lavapipe (`scripts/gpu-lavapipe.sh`, `testing/crates/gpu-budgets`): one submit a region. The row in `budgets.toml` points there. "One submit per op when not merged" is not counted anywhere.
- **The firmware rows** take their limits from `scripts/ci.d/chip.sh`. The loaded mode's 17,920 B is above the design's 12 KiB, as D7 set it. Dev's values per mode are not known, only the design's range.
- **`scripts/bench-compare.py`** is carried from dev unchanged, for the timing comparison, and the harness has a criterion bench for it. The comparison never fails the workflow.

- `core/host/src/io.rs`: `Host::feed_inline`, which feeds up to 16 bytes of plain data in place with the port's own type and memory space. The harness needs a feed that allocates nothing.
