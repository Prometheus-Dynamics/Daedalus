## Build

- The planner already accepts a list or struct constant for a list or struct type (`core/planner/src/solve/consts.rs`, `expr_accepts`). The refusal "port `x` can't be set from a constant" comes from the CPU backend, which has a decoder only where `T: FromLiteral` (`backends/cpu/src/steps/setup.rs`, `LitOf::DECODE`).
- `FromLiteral` gains impls for `Vec<T>` and `[T; N]` where `T: FromLiteral` (the alloc feature for `Vec`), and a derive, `#[derive(FromLiteral)]`, for structs with named fields. The derive reads each field by name from `Literal::Struct`, and a missing field takes its `Default` only if it has one, else the decode is refused.
- The CPU path is unchanged: the decoder is picked up through the same `LitOf` specialisation, so a list or struct port needs nothing more. Decoding happens once at planning and the value is shared, so running allocates nothing new.
- A constant that decodes to nothing keeps the current message, with the reason from the decoder when there is one.

## Proof

`core/types/tests/literal_lists.rs`: list and array decode, nested lists, wrong-kind and wrong-length refusals, and the derived struct decoding by field name. `testing/crates/planner/tests/j3_literals.rs`: a graph whose node takes a list constant and a struct constant plans, loads and runs with the decoded values, and a constant of the wrong shape is still refused at planning.
