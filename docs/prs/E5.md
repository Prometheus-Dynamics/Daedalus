## Build

- `compile(region)` for a region whose nodes all have wgpu bodies records every node's dispatch into one command encoder, in region order, one compute pass per node. It returns Compiled::Steps with one Step that covers every node in the region (`covers` lists them all).
- The wgpu backend returns only Steps. Blob and Source are refused, since a GPU is not a chip target. The design's generated-source form does not apply here.
- Values between nodes of one region stay on the GPU as storage owned by the region. Nothing is read back and no transfer is planned between them. Their buffers come from E2 at load.
- One queue submit per region run: flush uploads (E3), encode, submit, and return the submission as a fence (E8). Wgpu inserts the barriers between passes of one encoder.
- Dev's path is replaced: `dispatch_shader_with_options` made an encoder, submitted, blocked on the throttle and blocked on readback for every node. Dev's blocking helpers go. The planner's gpu_segments.rs union over GPU-GPU edges is replaced by B8 regions. Dev grouped two GPU nodes into one segment whenever an edge joined them, even when the edge is not per-pixel; a region is a convex set on one backend.
- Refusal: a body whose pipeline fails validation on the device is refused at compile, naming the node. The planner removes it from this backend and assigns again, until nothing is refused.
- Faults: a failing wgpu error inside the Step returns StepEnd::Fault. `at` names the node if the error says which one, and `covers` always lists the region.
- Exception to the no-heap rule, decided here for the owner to confirm: a wgpu submit allocates inside wgpu (dev measured about 29 allocations per submit). The region Step is therefore not allocation-free. Its allocation count must not grow with the node count. E7 gives the allocation-free alternative (the raw submitter ring).
- E7 adds the recording body kind to this region loop, in its own record.rs.
- Settled: an incoming import goes in the region's own submit. A chain of import, shader and export is one step.

## Proof

CI, lavapipe: a region of 8 whole-shader nodes (add and copy shaders from E4) runs with exactly 1 queue submit and 8 compute passes, counted by a test hook on the backend, and its values equal the sequential CPU reference. A region whose intermediate value has a consumer in another region reads back exactly once at the boundary (TransferStats). Allocation count of a region Step with 8 nodes is within a fixed slack of the count with 1 node (the exception is measured, not hidden).

## Status

Done, and run here on hardware and on lavapipe. The V3D timing is written in `testing/board-runs/E5.md` and hasn't been taken.

**For the owner to confirm: the allocation exception.** A region step with one node allocates 32 times a run, and with eight nodes 102 times, so about 10 for each extra pass. The brief asks that the count not grow with the node count. It does, and the growth is inside wgpu: recording a compute pass allocates there. A test in E4 shows a pass through this backend allocates no more than the same pass written on wgpu directly, so nothing of ours is in the 10. The test here holds the growth to 12 per pass and one node to 64. E7's raw submitter is the path that allocates nothing.

Differences from the brief:

- The runner ran a step again while its last fence was still pending, which a region step can't survive: it would publish over outputs nobody had been woken for. #103 fixed that in the runner first. A region therefore has one submission unfinished at a time, and E8's device-wide limit of two applies to `Shader::run` only.
- A node's ports are tied to its shader's bindings at compile time. `ShaderSpec` gained `inputs` and `outputs`: for each declared port, the position of the binding it feeds. The authoring macro fills them with a const function, so a declared port that names no binding fails the build.
- A value on the device is an `Arc<Storage>` in a typed cell. A buffer that leaves the region is handed to the runner each run, so the region keeps up to four per output and reuses one that nobody else still holds. A buffer used only inside the region is one buffer, reused every run.
- Buffers are sized when the region first runs, and again if an input's size changes, since a size isn't known before the first value arrives. The rule: a written buffer has as many elements as the first array the shader reads, or `bytes.<port>` from the node's metadata says outright. A shader that reads no array and has no such metadata is refused at compile, naming the node and the port.
- Only storage buffers can be a shader node's output so far. A node that writes a storage texture is refused by name. Texture inputs work.
- A uniform is fed by an input port whose value is bytes, and a uniform no port feeds is zeroes.
- "Reads back exactly once at the boundary" needs the transfers of E3, so it isn't tested here. What is tested: a value read both inside the region and outside it is one buffer, published once, in one submit.
- Uploads aren't flushed before the submit yet, also E3. Timestamps aren't taken per pass in a region: a region's ticket reports submit-to-done.
- Imports absorbed into the region's submit arrive with E14, so `absorbed` is empty.

### Added after: a region is one compute pass (`one-pass`)

A region recorded a compute pass for each node. It now keeps one pass open and records each shader node's dispatch into it: in a compute pass each dispatch is its own scope for what it reads and writes, so a node reads what the node before wrote. The pass ends for anything that isn't a dispatch: a recording body, a draw, or a uniform filled from a buffer, which needs a copy. `ShaderStats` counts both: `passes` begun and `dispatches`, the times a shader ran. Merging is shown by dispatches, since a pass no longer says how many shaders ran.

Measured: an eight-node region allocates 44 times a warm run, where it allocated 102. About 2 a node, where it was 10. The 32 that remain for a one-node region are what one op recorded and submitted alone allocates through wgpu: the region adds nothing to that.
