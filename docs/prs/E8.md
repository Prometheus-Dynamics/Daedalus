## Build

- A region's Step returns StepEnd::Pending(Fence) carrying the wgpu submission index. The Runner (C2) polls it with a non-blocking poll on each tick. A tick never waits.
- In-flight limit: dev allowed 2 submissions per device, and blocked on the oldest when a third arrived. Here the Step returns Pending on the oldest instead. The limit of 2 stays, as a hidden setting.
- Bounded waits: any wait the backend itself needs (setup, shutdown, tests) uses a bound. The default is 5 s (dev wait.rs; `DAEDALUS_GPU_WAIT_TIMEOUT_MS` moves to Host settings). A timeout returns a Fault and marks the device lost (E11).
- Uncaptured errors: the device's error callback stores messages (cap 16, joined). The next region Step that dispatched work returns a Fault, so a node never uses output the driver flagged as suspect (dev wait.rs:45-76, commit 5100c74).
- Dropped: poll_driver.rs, the thread pool with 2 shared workers and 2 overflow threads. No thread polls the device. A bounded wait runs on the caller's thread during setup or shutdown only.
- Dropped: GpuInFlight and its latest-wins drop_oldest policy. That is a node-level policy and belongs to C4 backpressure. The ticket type becomes the Pending fence.
- Timers (dev gpu_timer.rs): timestamp queries where the device has them, otherwise submit-to-done. GpuTimeSource says which one was used. The duration reaches telemetry (C11).
- scripts/check-gpu-async-blocking.sh is rewritten for the new design: it fails on any `PollType::Wait` or `pollster::block_on` in backends/wgpu/src outside wait.rs and setup modules.

## Status

Done, and run here on hardware. lavapipe runs it in the GPU lane of CI. The V3D poll cost is written in `testing/board-runs/E8.md` and hasn't been measured.

Differences from the brief:

- Regions don't have steps until E5, so the pieces are built on `Shader::run`, which E5's step will call. `run` never waits. It returns `Run::Started(ticket)`, or `Run::Busy(oldest)` without submitting when the device already has its limit of submissions unfinished. `Ticket::into_fence` gives the `Fence` a step returns in `StepEnd::Pending`.
- A fence carries one word, so what it stands for is kept in a table until the fence resolves. A fence that is dropped without being polled to the end leaves a small entry behind.
- A fence fails when the device reported an error while its work ran, or the device is lost.
- An uncaptured error fails the next `run`, before anything is submitted, and fails a `Ticket::wait` on work it arrived during.
- The wait bound and the in-flight limit are fields of `Options` (`wait_timeout`, and the hidden `max_in_flight`). Nothing reads the environment.
- A timed-out wait marks the device lost, and nothing more runs on it. Replacing a lost device is E11.
- Timers: `Shader::with_timestamps` times each pass with the device's own timestamps where it has them, and `Ticket::gpu_time` says which source it used. Reaching telemetry waits for E5, which has the step.
- The blocking check allows `wait.rs` and `driver.rs`, which is where device setup blocks.
- The device tests set how much work they submit by measuring the device, and lengthen it when it turns out too short, because tests beside them share the GPU.
