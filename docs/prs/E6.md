## Build

- Dev has no merging. Each GPU node is one shader and one submit. This PR merges pixel chains, as the design's first GPU level requires.
- Pixel body: a node declared `backend = wgpu(pixel)` with one WGSL function `fn apply(c: T_in, cfg: Cfg) -> T_out`, and no other access to its input. wgpu-author (pixel.rs) renames every top-level name in the body with a prefix from the node id at expansion, so bodies concatenate without clashes. A body with neighbourhood reads, workgroup memory, barriers or atomics is not a pixel body and fails to expand.
- Merge rule (exact): a chain is n1..nk, k >= 2, in one region, with an edge from n(i-1) to n(i) that is an input of n(i). n(i) reads that input only at the same pixel. Every node in the chain is a pixel body. Output of n(i), for i < k, has exactly one consumer, which is n(i+1). A second consumer, inside or outside the region, ends the chain at n(i). The chain's type keys match: T_out of n(i) equals T_in of n(i+1). A conversion between them merges only when it is itself a pixel body.
- Side inputs: a node may take other inputs that it reads at the same pixel from their own buffers. Each one is a binding. Any other access makes the node not a pixel body.
- Bindings: the head's input is binding 0 and the tail's output is binding 1. Every node's config and its side inputs follow in chain order, with unique binding numbers. Each binding is counted against the limits below.
- Limits: a merged shader must fit the device's limits (E1: storage buffers and storage textures per stage, workgroup storage, invocations) and the portable floor WEBGPU_DEFAULTS. A chain that does not fit is split into the longest prefixes that fit, and each segment is its own shader. A single node that does not fit alone is refused, and the planner reassigns it.
- Generation at compile: compute form writes one `@compute` entry `main` with the head's workgroup size. It loads the input at the invocation's index, then applies each node in order (`let c1 = apply_1(c0, cfg_1);`), then stores the result. Intermediate values stay in registers. Nothing is written for intermediates.
- Fragment form for tile-based devices (profile flag from E1): one render pass per segment, with the same bodies and the pipeline builder from E7. Dev measured the fragment pass on V3D at 2.83 ms against 36.4 ms for storage-buffer compute (gpu-nodes.md, box 3x3 on 1280x800), so V3D takes the fragment form.
- Cache: key = stable hash (FNV-1a 64) over the ordered node ids, each body's source hash computed at expansion, the binding table, the workgroup size, the form, the output formats and the device key. Pipelines are cached per device with the dev limit of 128. Wgpu's pipeline cache file is written by the Host's schedule (C10), as dev does.
- Output: integer formats are bit-exact against the unmerged chain. Float formats match the unmerged chain within the tolerance dev's float kernel tests use.

## Proof

CI, lavapipe, both forms: a chain of 4 integer pixel nodes equals the unmerged chain bit-exact (new). A node that reads x+1 inside a chain splits it into two shaders (new). A node with a second consumer ends the chain (new). A 9-node chain where each node has one storage parameter splits into segments that each fit WEBGPU_DEFAULTS (new). Compiling the same chain twice creates one pipeline (counter). Golden key test for a fixed chain. Ported: every_target_format_renders_and_reads_back and pass_reads_inputs_at_its_own_pixel, now run on a merged fragment chain. A merged chain of two test per-pixel functions gives the same output as the two run separately.

## Status

Done for the compute form, which is what a region uses. The fragment form is generated and runs, and is tested against the compute form bit for bit, but a region doesn't pick it yet: see the first difference. Run here on hardware and on lavapipe. The V3D timing is written in `testing/board-runs/E6.md` and hasn't been taken.

Differences from the brief:

- **Resolved by E15:** a chain that is given a texture now runs as the fragment form in a region. What follows is how this PR left it. **A region always merges into the compute form.** A region's values are storage buffers, and the fragment form reads and writes textures. `merge::fragment_pass` builds the merged fragment pass for a chain and a target format, and a test runs it against the compute form on the same pixels. Choosing it in a region on a tile-based device needs textures as region values, which is E15's subject. Until then V3D gets the compute form, which dev measured as much the slower one there.
- A pixel body is `backend = daedalus_wgpu_author(pixel, ..)` on a const holding `fn apply(c: T, ..) -> U`. After the pixel, a parameter named `cfg` is the node's config, a struct bound as a uniform, and any other parameter is a side input read at the same pixel from a buffer of its own. Each parameter is fed by the port of its name, and a config no port feeds is zeroes.
- Names are prefixed when the bodies are put together, not at expansion, with the node's position in the chain: the same node can be in a chain twice. The macro records the body's top-level names, and refuses a body where one of them is also a member, parameter or local name, since those aren't prefixed.
- What makes a body not a pixel body is checked by the macro on naga's reading of it: any global, any entry point, an atomic, a barrier, workgroup memory or a texture write. A node that reads a neighbour therefore has to be a whole shader, and it cuts a chain into the part before it and the part after.
- A chain is one or more nodes: a pixel body with no pixel neighbour is a chain of one, and still runs as a generated shader.
- A merged chain runs where its last node stands in the region. Everything any of its nodes reads is made before that.
- The binding limits a chain is cut to are the storage buffers every device allows (8) or the device's own if lower, and 12 uniform buffers. Storage textures, workgroup memory and invocation counts can't be exceeded by a generated compute pass, which has none of the first two and a fixed workgroup of 64.
- Generated shaders are kept for the life of the process, once per distinct chain, because a loaded shader's text has to outlive anything that might load it again, such as the rebuild after a lost device. Pipelines are cached per device under the shader's own content key, as every shader's is. There is no separate limit of 128.
- The chain key is FNV-1a over each node's name and source hash, the binding table, the workgroup size and the form, pinned by a test whose value was computed independently. The output format isn't in it for the compute form, which has none, and the device isn't in it because the pipeline cache is already per device.
- Float tolerance isn't tested: the merged shader calls the same functions on the same values, and the tests are on integers, where equality is exact.
- Status (element-wise rename): the merged form is now called element-wise. Where this brief says `wgpu(pixel)` the macro form is `daedalus_wgpu_author(element, ..)`; `pixel.rs` is `backends/wgpu-author/src/element.rs`; `PixelSpec` is `ElementSpec`. The 04_gpu example's `fragment` binary is `element`.
