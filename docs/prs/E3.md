## Build

- Transfer entries offered to the planner (A7 Transfer): host to device (upload), device to host (readback), and the host-cached and host-mapped spaces from E2. Each entry has a fixed cost class, so planning never measures a device.
- A transfer is a planned edge. Dev's rule that a transfer inside a handler is invisible to the plan (gpu-nodes.md, Transfers as plan edges) is gone: no node body copies data across a space.
- Upload: `write` takes CPU bytes into a storage or texture. Wgpu's queue writes flush with the next submit, so the region flushes uploads before it encodes. Raw submits (E7) see upload data only after the same flush.
- Readback: the producing region copies its outputs into a pooled staging buffer in the same encoder. The copy completes through a fence (E8). The Step never blocks to read. `read_into` (blocking) is for setup and tests only.
- TransferStats (dev buffer.rs) counts uploads and downloads in bytes and in count. Tests read these counters to prove where transfers happened, so the counters stay.
- Dropped: the row-by-row re-pitch upload (dev texture_transfer.rs, 21 ms at 640x480 on V3D) is not carried. E15 replaces it for imported images with the fold path, and nothing else needs it.

## Status

Done, and run here on hardware and on lavapipe. The V3D timings are written in `testing/board-runs/E3.md` and haven't been taken.

Differences from the brief:

- A value on the device is a `Storage`, in whichever of the backend's memory spaces it was made, and a transfer here is for any type. So the moves are between spaces of buffers, not between a buffer and a Rust type: turning bytes into an author's own type is a `#[transfer]` or a node of theirs.
- Device to host is two entries: `wgpu.readback` copies a device buffer into a host-mapped one (cost copy), and `wgpu.map` hands a host-mapped, host-cached or dma-heap buffer to the host as it is (cost import). The readback is a copy on the device that completes through a fence, so the step never waits and never maps, and nothing is filled in after it was published. The brief's staging copy inside the producing region isn't needed for that, and a region doesn't know which of its outputs will be read back.
- Host to device is `wgpu.upload` into device memory and `wgpu.upload.mapped` into a host-mapped buffer written in place. Both copy a value's bytes into a buffer of the step's own, reused once its last consumer has dropped it. A value with no bytes, such as a typed Rust value, faults: it needs the author's own transfer.
- wgpu flushes queue writes with the next submit on the queue by itself, so a region doesn't flush uploads separately.
- A transfer's step is made by a plain function that can't see its backend. A readback finds the device from its input. An upload goes to the device a backend opened most recently, or the one the process shares.
- A uniform fed through an upload arrives as a buffer, so a region copies it into the shader's uniform in the same submit, ahead of the pass (`Bound::UniformFrom`).
- `Texture::write` and `Texture::read_into` are added. `read_into` waits and is for setup and tests, like `Storage::read_into`. Every format round-trips bit for bit at a width whose rows need padding.
- `TransferStats` counts uploads and downloads, in count and bytes, per device.
- The planner-level test with two spaces on the sim backend is B9's, and isn't repeated. Here `find_transfer` is run over this backend's own table: host to device is one upload, device to host is never one hop, and every space is one hop from the host.

### Added after: host ports and typed values (`E3-typed`)

Found by I8, the first graph run from the host through the planner to the GPU and back. Two things were missing, and nothing could be fed to a shader node from a host port or a CPU node.

- **The backend named no host memory, so the planner put host ports on the device and inserted no upload or readback.** It now lists the host's space, `cpu.host`, last and unreadable by shaders. A host port's value is then on the host, and the way to and from a shader node is the upload and the readback. A host that wants to feed and take `Storage` with no copy sets `Options::host_ports_on_device`.
- **A value of an author's own type had no way across**, since an upload moves bytes and a `#[transfer]` isn't bound by the loader. `HostBytes` is two functions, the bytes of a value and a value from bytes, and `WgpuBackend::with_bytes::<T>()` adds two moves for exactly that type: `wgpu.upload:<key>` from the host to device memory, and `wgpu.map:<key>` from a host-readable buffer to the host as a `T`. The planner prefers them to the any-type ones. Both copy, and the second allocates the value it makes, each tick.
- A buffer is a whole number of words, so a value that comes back can have up to three bytes of zeroes after what went up. `from_bytes` is told so.
- Still not there: a `#[transfer]` function written by an author is planned and not run, for any backend. The host also has no call that waits for a device: a graph with a step waiting on one is ticked again until its output arrives.
