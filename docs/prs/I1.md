## Build

- A pure test fixture. It is a software model of an NPU: a fake device with its own memory space id (for example 'fake-npu:sram'), a transfer table to and from host memory, and a fixed cost per op. Nothing in it touches hardware.
- testing/crates/fake-npu-author is the authoring crate. It exports the authoring macro that the #[node] macro calls for backend = fake_npu(model = '...'). It is the only part a node author depends on.
- testing/crates/fake-npu implements core/backend's Backend trait (A7): id, memory, transfers, can_take, compile. compile returns Compiled::Steps for ops it supports and refuses any op outside a fixed list, so the planner's refusal round (B8) is exercised.
- testing/crates/fake-npu-plugin is a cdylib that carries the backend and two or three nodes. It is loaded through the G2 loader like any other dylib plugin. It exports nothing the core needs beyond the stable handshake.
- The PR changes no file outside its creates list. In particular it changes nothing under core/, backends/cpu or the authoring crates. Adding a backend needs no change to Daedalus, and that is the point of the test.
- Name nothing NPU-specific in core/. The gate's boundary check (A2) already forbids the words gpu, npu, shader, frame and so on under core/; this PR's test asserts that the words 'npu' and 'fake' do not appear under core/ or backends/cpu.
- Tests (in testing/crates/fake-npu-plugin/tests/): loads_as_plugin (the backend is registered from the dylib alone); node_runs_on_fake_npu (a graph with one fake NPU node and CPU nodes runs and its output matches a CPU-only run); unsupported_op_refused_and_reassigned (an op the backend refuses is run on CPU after one refusal round, and the report names the refusal); transfer_path_planned (a graph that crosses CPU to fake NPU uses the transfer table entry, and a planning error names the ports and spaces when the table has no entry); reload_keeps_backend (a reload of the plugin keeps the node on its body, or reports a change).
- Compile-fail case: a fake-NPU node naming a backend path that is not in scope fails with an error that names the path.

## Proof

scripts/ci.sh test runs tests named loads_as_plugin, node_runs_on_fake_npu, unsupported_op_refused_and_reassigned, transfer_path_planned and reload_keeps_backend, and the trybuild case in testing/crates/fake-npu-author. ## Status

Done. `testing/crates/fake-npu-author`, `testing/crates/fake-npu` and `testing/crates/fake-npu-plugin` are a backend Daedalus had never heard of, written against `core/backend` and shipped as a dylib plugin. The PR adds those three directories and changes nothing else in the code: no file under `core/`, `backends/` or the authoring crates.

As built:

- **`fake-npu-author`** exports `__daedalus_body!`, which `#[node(backend = daedalus_fake_npu_author(model = "<name>", <port>: <Type>, ..))]` on a const expands to. A function body is a compile error that says a node here is a const naming a model.
- **`fake-npu`** is the device: the memory space `fake-npu:sram`, a transfer table of `fake-npu.upload` and `fake-npu.download` between it and host memory (`cpu.host`), three ops (`scale2`, `add1`, `negate`) at 1,000 ns of device time each, and counters. `FakeNpu` is the backend linked in. It takes every node offered to it and refuses, when a region is compiled, any node whose model is not one of the three. `PluginNpu` is the same backend over a loaded plugin's table.
- **`fake-npu-plugin`** is a `cdylib` (and an `rlib`, so its own tests can be built) exporting the one entry symbol, with the backend `fake-npu` and the nodes `npu.scale`, `npu.add` and `npu.negate`.

Tests, in `testing/crates/fake-npu-plugin/tests/npu.rs`:

- `loads_as_plugin`: the library gives the backend and three nodes, they join a registry that had none of them, and a graph with one plans onto the backend.
- `node_runs_on_fake_npu`: `inc -> npu.scale -> inc` with the middle node on the plugin's backend gives the same outputs as the same graph run on the CPU alone, for five inputs.
- `unsupported_op_refused_and_reassigned`: a node with a model the device lacks and a CPU body, between two nodes the device runs, is given to the device, refused, and runs on the CPU after one more round (`rounds == 2`). With no CPU body, planning fails with `fake-npu: refused (the fake NPU has no op `sqrt` ..)`.
- `transfer_path_planned`: the plan uses `fake-npu.upload` and `fake-npu.download`, on the edges into and out of the node. With an empty transfer table, planning fails naming the port, `cpu.host` and `fake-npu:sram`.
- `reload_keeps_backend`: a reload with the same plugin carries the node. After the plugin is loaded again (generation 2) the node is still on the fake NPU and the reload reports it as fresh.
- `the_core_and_the_cpu_backend_name_no_npu`: no `npu` as a word, and no `fake_npu` or `fake-npu`, in any `.rs` or `.toml` under `core/` or `backends/cpu`.

And `testing/crates/fake-npu-author/tests/ui.rs` (trybuild): a node naming `acme_npu_author`, which is not in scope, fails with "cannot find module or crate `acme_npu_author`"; a function body fails with the macro's message; a model const compiles.

Differences from the brief:

- **A plugin's table carries no memory spaces and no transfers** (G2), so `PluginNpu` supplies them on the host's side, from the `fake-npu` crate. The steps and the node declarations come from the library. A plugin that brought its own transfer table would need the plugin contract extended.
- **A plan that succeeded keeps the number of rounds, not the refusals.** "The report names the refusal" is shown two ways: the round count on the plan that reassigned the node, and the refusal's text in the error when there is nowhere else for it to go.
- **The refused node sits between two NPU nodes.** With CPU neighbours the planner never offers it to the device at all, since the CPU body crosses between backends less.
- **`fake` already appears under `core/`** (a test backend called `Fake`, and a comment), so the grep test checks `npu` as a word and the two spellings of this backend's name.
- **The op counter of the plugin is inside the library**, which has its own copy of it. The test of the plugin checks the transfers, counted on the host's side, and the test of the linked backend checks the ops and their cost.
- **The plugin's library is found beside the test binary**, where cargo puts it when it builds the crate for its tests. No nested build.
- **"Touches only the three creates paths"** was checked with `git status` before this section and the TODO tick were added.

Nothing here was run on Windows: clippy for the gnu target only.
