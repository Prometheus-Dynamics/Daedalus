## Build

- The data-parallel ops of the kernels library, on GPU-resident storage: RGB, RGBA and gray layouts, LE f32, binary16 to f32, f32 to unorm8, byte copies, hex and base64 encode and decode (decode reports the decoded length and invalid input), and chunked CRC32. D8 holds the CPU reference.
- Per-pixel float ops such as f32_to_unorm8 are declared as pixel bodies (`wgpu(pixel)`), so E6 can merge them. The others are whole-shader bodies.
- The kernels are library functions, not nodes (design: kernels are not nodes). A node calls them in its body or region.
- Copy engine: `copy_with_engine` stays as an op, with the copy command, not as a special path.
- Bit-exact against D8's reference for every op, as dev's kernels tests check.
- Dropped: dev's FRAGMENT_WIDTH constant path. Per-pixel ops reach the fragment form through E6, so this PR keeps one path per op.
- Settled: no pixel-format conversions. They are image operations, which nodes provide.

## Proof

## Status

Done. Every op is checked bit for bit against D8's reference, on hardware (RADV) and on lavapipe: f16 to f32 over every binary16 value, f32 to unorm8 over the rounding halves, NaNs, infinities and subnormals, and the byte ops at lengths around word, group and chunk boundaries. The CM5 timings are written in `testing/board-runs/E16.md` and haven't been taken.

Differences from the brief:

- **No RGB, RGBA or gray layout ops.** The brief lists them and also settles that pixel-format conversions are image operations which nodes provide. D8 has no reference for them, so there is nothing to be exact against. The ops are f32 from LE, f16 to f32, f32 to unorm8, copy, hex, base64 encode and decode, and chunked CRC-32.
- `Kernels::new(&backend)` holds the ops for one device, and a shader is built the first time its op is used. `encode` records one pass into a caller's encoder, `run` submits one alone, and `Kernels::in_record(cx)` gives them to a recording body (E7), whose `RecordCx` now carries the device they are made on. After a lost device is replaced, a caller makes another: `device_key` says which device one is on.
- **Nothing here waits unless asked.** `base64_decode` and `crc32` submit and return a `Decoding` or a `Checksum`, and its `wait` reads the result. Dev's waited inside the call.
- Base64 decode is only `base64_decode`: through `encode` it is refused, since it would have nowhere to report. Each decode has its own report buffer, so two in flight don't share one. Invalid input is `KernelError::InvalidSymbol { at }`, at the offset the CPU decoder gives, which the test checks against it.
- The counts of a run are a uniform, copied into it by the same encoder that records the pass, so two runs of one op in one encoder each see their own. The small buffers holding them are kept by value, up to 64.
- **The per-value float functions are pixel bodies as well as ops, which is two ways to reach them.** `HALF_TO_F32` and `F32_TO_UNORM8` are `PixelSpec`s over one `u32` a value, so E6 merges them with any chain, and `merge::chain_shader` (new, public) runs a chain by hand. The ops `F16ToF32` and `F32ToUnorm8` stay, because they read packed halves and write packed bytes, which a pixel body can't: it is one element in and one out. Both call the same WGSL function, in `common.wgsl`, which holds only functions of one value. `kernels.wgsl` holds the bindings and entry points.
- The pixel bodies take and return bits in a `u32`, not `f32`, so a NaN's payload survives and the result can be compared exactly.
- `copy_with_engine` records the copy command and counts no pass. It refuses a length that isn't a multiple of 4 or a buffer on another device.
- An op over more bytes than a 32-bit offset reaches, or more workgroups than the device dispatches in two dimensions, is refused with `KernelError::Size`.
- The backend depends on `daedalus-kernels-sys` for `crc32_combine`, which puts the chunk CRCs together on the host.
- Dev's inventory evidence and its per-op timing in the test aren't ported: the tests here are correctness only, and the timings belong to the board run and to E12's budgets.

### Added after: the counts are bound, not copied (`batching-match`)

The counts of a run were a uniform filled by a buffer copy recorded before each pass. On the CM5 that copy between passes cost about a quarter of a millisecond over eight ops. They are now a small read-only storage buffer for each distinct set of counts, bound as it is, which is what dev did. The ops' results are unchanged.

### Added after: a batch of ops (`one-pass`)

`Kernels::batch()` records several ops into one compute pass and submits them once. Eight 64 KiB copies in a batch take 0.068 ms on an RX 6800 XT, where eight passes in one submit took 0.136 ms.

## Removed

What this PR built has been removed from the tree. It was carried over from `dev` and nothing in Daedalus used it: the runtime calls no byte kernel, and no graph planned through a memory-only backend. The text above is kept as the record of what was built.
- Status (element-wise rename): the merged form is now called element-wise. Where this brief says `wgpu(pixel)` the macro form is `daedalus_wgpu_author(element, ..)`; `pixel.rs` is `backends/wgpu-author/src/element.rs`; `PixelSpec` is `ElementSpec`. The 04_gpu example's `fragment` binary is `element`.
