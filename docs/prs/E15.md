## Build

- Storage import: a dma-buf image becomes a storage buffer through E14's import. The cache is keyed by dma-buf identity (dev, inode), with the stats dev keeps: hits, imports, evictions. Each plane's offset and stride is reported.
- The imported value is held until the GPU work that reads it completes. The hold is a Pending fence (E8), and it ends when the fence completes.
- Format check on this path: refuse Bayer and compressed images. Dev's from_frame_view refuses them, but dev's GPU cache import (gpu_storage/frames.rs) does not check, so it imports any dma-buf planes. This PR fixes that gap.
- Padding: the dma-buf must cover the driver's padding (V3D 256 bytes past the last plane). A producer that allocated without slack requests a larger buffer. The backend never clamps.
- Sampling a camera image on V3D: a buffer-to-image copy uses the texture formatting unit (TFU) for a whole image from offset 0. Dev measured 0.49 ms at 640x480 XRGB and 0.71 ms at 1280x720, against 2.9 and 8.6 ms for a shader copy. A stride that is a multiple of 256 bytes takes this path directly.
- Folded strides: a stride that is not a multiple of 256 (640-byte GREY rows) folds k rows side by side (k = 2 for 640), so one direct copy fills a wider texture, and a small fragment pass unfolds it. Dev measured 0.43 ms against 0.27 ms for the aligned stride. Row-by-row re-pitch (21 ms at 640x480) remains only for strides whose fold would be too wide.
- images allocated with 256-aligned strides take the direct path.

## Status

Done. Run here on hardware (RADV, dma-bufs from the system heap) and on lavapipe, where the dma-buf import test stops at the driver's typed refusal. The V3D timings are written in `testing/board-runs/E15.md` and haven't been taken: nothing here says the fold or the direct copy is as fast on V3D as dev measured.

Differences from the brief:

- **The hold isn't a fence of its own.** A region step keeps a share of every typed value it read (`daedalus_runner::share_typed`, new in the runner) from its submit until its next run. The runner holds a step whose fence is pending (#103), so the next run starts only when the device has finished reading, and that is when the shares are dropped. An imported texture keeps the value it was imported from (`Texture::holds_its_source`) for as long as the texture lives. With both, the import step's ring of the last four values (E14) is gone.
- **A merged pixel chain that is given a texture runs as one fragment pass and writes a texture.** This closes E6's deferral. The form is chosen by what the value is, not by the device profile: a chain fed a buffer is the compute pass it was, and the same step takes either from one run to the next. Its other pixel inputs must then be textures too, and a mix is a fault that says so. A config is a port's bytes, an uploaded buffer, or zeroes, as in the compute form. The targets are the chain's own, and one is drawn to again once nobody else holds it. The bind group is made each run and not cached.
- Storage import is `WgpuBackend::import_storage(ExternalBuffer) -> ImportedStorage`: the dma-buf as a storage buffer with each plane's offset and stride, cached by the dma-buf's identity with `storage_import_stats` (hits, imports, evictions). `ImageKind::of(fourcc)` refuses Bayer and compressed fourccs here, which dev's cache import didn't. A fourcc the table doesn't know is taken as pixels.
- The copy is `ImageCopy::new(backend, desc, stride)`, which owns its texture and picks a `Plan` once: `Direct` for a stride that is a multiple of 256 bytes, `Folded { rows }`, or `Rows`. `encode` records it into a caller's encoder and `run` submits it alone.
- **A fold needs the height to be a multiple of the rows folded**, the stride to be whole pixels, and the folded width to fit the device. Anything else goes row by row. A folded copy that would read past the end of its buffer (the last row's padding isn't there) also goes row by row for that image, and never reads short.
- Whether the direct copy takes V3D's TFU is the driver's choice. This PR arranges what dev found it needs (whole image, offset 0, 256-aligned rows) and can't observe it off the board.
- The padding rule (V3D's 256 bytes past the last plane) is E14's `Importer`, used by both imports. It isn't written twice.
- Dev's mock image tests (`mock_imports_frame_views`, `mock_import_waits_for_a_late_fence`) aren't ported: there is no mock device here. What they covered is tested on the real paths: the description checks with no fds (E14), the late fence on a real exported fence (E14), and the hold in `a_region_keeps_what_it_read_until_its_next_run` and the import tests.
- `ImageCopy` isn't a transfer the planner inserts yet. A type's owner calls it from a recorded body (E7). Offering it as a transfer for an image type is the owner's `#[transfer]`, as `import_transfer` is.
- Status (element-wise rename): the merged form is now called element-wise. Where this brief says `wgpu(pixel)` the macro form is `daedalus_wgpu_author(element, ..)`; `pixel.rs` is `backends/wgpu-author/src/element.rs`; `PixelSpec` is `ElementSpec`. The 04_gpu example's `fragment` binary is `element`.
