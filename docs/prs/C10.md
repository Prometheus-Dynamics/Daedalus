## Build

- load(plan): allocates the slots, the pools, the Bits, the fence list and the telemetry arrays once. start() begins ticking. Load from a Blob belongs to D3; this PR loads an in-memory plan.
- reload(new_plan): match nodes by node key. A node with the same body keeps its state (C9). A node whose body changed starts fresh, and the change is reported. Removed nodes lose their state, which is dropped exactly once.
- Held values (d543c6c): a node that holds a value keeps it with its state across a reload. A reload without that node releases the value exactly once. Test a_graph_reload_carries_held_frames_or_releases_them.
- Host ports removed by the reload drop their queued and held values, and the report says how many.
- A reload to a plan built for other host bridges is refused. A failed compile or load keeps the running graph unchanged.
- The report (report.rs) lists carried, fresh, dropped and removed-port counts, with bounded lists of names.

## Proof

core/host/tests/reload.rs ports the reload cases of host_graph_reload.rs: carries state of kept nodes; removed node state is dropped and reported; a failed compile keeps the running graph; reload rejects a graph on other bridges. A counting Drop type confirms a held value is released exactly once. The d543c6c case is ported with its value logic.

## Fixed after merge (`C10-fix`)

**A reload reported a node's state as carried and then dropped it.** A node's state is in its step's data (C9), and a reload compiled every step again, so a CPU node with `state(T)` started over on every reload while the report listed it under `carried`. Only the host's `StateStore` entries were carried.

A reload now moves a step across as it is when it is the same step in both plans: it covers the same nodes, at the same places in the graph, with the same bodies (the same node id on the same backend at the same version), the same constants and the same ports. The step compiled for the new plan takes its place in the old runner and is released with it. A node whose step did not move starts fresh, loses its `StateStore` entries, and is reported under `fresh`. A node with no step, as a host bridge has none, is still carried by its body alone.

What follows from it:

- Nodes a backend merged into one step are kept or started fresh together. A graph that wants one node to keep its state while its neighbour changes keeps them in separate steps (`daedalus.node.fusion` set to false on the node, or merging off).
- A node whose constants changed, or that is at another index in the graph, starts fresh. Its step holds the constants, and names its node by index when it reports a failure.
- A step that is waiting on a fence is not moved.
- Another version of a backend is another body, so a plugin loaded again starts its nodes fresh.

`Runner::swap_step` and `Planned::backend` are the two additions. `backends/cpu/tests/reload_state.rs` has the tests.
