## Build

- Progress cells are `Progress` atomics owned by the run's buffers (`core/runner/src/owned_run.rs`). The host reads them through `LoadedHost::node_progress(&self)`, which needs the host itself, so a thread running `tick_parallel` (which holds `&mut`) cannot read them.
- The buffers keep the progress cells behind an `Arc`, the same way the cancel word is kept. `RunBuffers::progress_handle()` returns a `ProgressHandle`: a clone of that `Arc`, which is `Send` and `Sync`.
- `LoadedHost::progress_handle(node)` gives a handle for one node, with the step index found at load (no name lookup while reading). Reading is a relaxed load of two atomics: no lock and no allocation.
- Writing is unchanged. A body writes through `cx.progress`, as before.
- A handle keeps the cells alive, so it may outlive the host; a read after the host is gone returns the last values.

## Proof

`core/runner/tests/progress_handle.rs`: a parallel tick on two workers, where one body reports progress while another thread reads the handle in a loop. The reader sees a value that increases and never a torn pair beyond the bounds the body wrote, the reads allocate nothing (the existing counting allocator), and a handle read after the host drops still returns the last values.
