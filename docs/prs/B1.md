## Build

- Pipeline: core/planner/src/pipeline.rs runs the solve stages in one fixed order. Only that file calls stages. Later PRs add their call there, marked by a comment. Each stage gets one Work value (the graph from A6, the registry view, and a diagnostics list). No global state.
- Stage order for this PR: expand groups, defaults, hydrate. Leave a marked slot between defaults and hydrate for the rewrite hook (B5). Dev runs lowerings before hydrate, so the same order holds.
- Catalog: a read-only view of the registry (A8), taken once per planning run. It answers node lookups and nothing else. It holds no transport or adapter state.
- Groups: a group node is replaced by its body graph. The body is a typed graph held by the A8 declaration, never a JSON string in metadata. Nested groups expand until none remain. Nesting deeper than 16 is a GroupDepth error that names the chain of groups.
- Group ports: an outer edge into a group input, or out of a group output, is wired to the body's host bridge node. An outer edge to a port the body does not expose is an error naming the group, the node and the port (dev reports this as PortMissing; keep the code).
- Stage labels: each body node is labelled group_label::label. Each carries the outermost group id, so nested stages roll up into one group.
- Host bridge: a boundary node kind from A6 with declared port types. This PR keeps those declared types on the solved node. B2 checks against them.
- Defaults: copy the declaration's fire mode and its required-input list onto the solved node. A value the graph sets wins. The declared execution kind is copied as-is.
- Hydrate: every node id must have at least one body in the registry view. Report every missing id in one pass, each once, with suggestions from edit distance (dev suggest.rs, same cutoff).
- Errors: solve::expand and solve::hydrate each define their own error enum. The pipeline returns them as a list. B11 turns them into diagnostics.
- The planner is a host crate: std and alloc, no no_std requirement. It may not depend on backends, interfaces, languages or service. The test crate testing/crates/planner is the only place that depends on backends/sim.
- No type or module is named after hardware or media (gpu, wgpu, shader, texture, frame, image, camera, npu, mcu).
- Dropped here: the malformed-metadata checks. A8 rejects an unparsable declaration at registration, so the planner never sees one. The planner's test for that moves to A8.
