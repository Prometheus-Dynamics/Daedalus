## Build

- Loss comes from the driver's lost callback, or from a bounded wait that timed out (E8). The device is marked lost, its device key is dropped, and its pools are cleared (E2).
- Every region on a lost device faults. The Fault names `covers`, and `at` when known. A region never silently uses output from a lost device.
- Retry: the backend reopens the device on the next region request, under the failure rule: never give up, backoff from 250 ms doubling, capped at 8 s. The design's cap is 8 s. Dev's runtime gpu_source.rs has RETRY_CAP of 5 s, and dev's engine test asserts 5 s, so that test changes to 8 s.
- No automatic off by default. A device that keeps failing keeps retrying on the schedule. Manual off is a Host setting. Automatic off exists only as a policy the operator sets (C5).
- A merged region that fails backs off and reports its covers and failing node. It does not unmerge by itself. Manual unmerged mode is C12.
- Dropped: the engine-side RetryingGpu and GpuSource wrapper as a separate type. The backend owns its retry state. The Host sees only Fault and the backoff delay.
- Dev has never verified real device loss on hardware (commit b6c83f5). Keep that note in the PR description until a board run exists.

## Proof

CI, lavapipe: a test-only mark_lost on a live device makes the next region Fault with its covers, the device reopens on the following request, and the region runs again (new). Backoff schedule test: after 100 failures the delay equals the cap (8 s) and never exceeds it, and no automatic off happens (ported and adapted from lazy_gpu_backoff.rs and lazy_gpu_reopen.rs).

## Status

Done, and run here on hardware and on lavapipe. Real device loss has never been verified on hardware, on dev or here: the test marks a live device lost. The V3D run that induces a real timeout is written in `testing/board-runs/E11.md` and hasn't happened.

Differences from the brief:

- A backend and the steps it compiled share a link to the device. When a region's step finds its device lost it asks the link for another, loads its shaders again on that one, and forgets its old buffers. That run faults, since what it was given is on the lost device, and the next run goes through. So the reopen happens on the run that sees the loss, not on a later one.
- The first attempt to open a device after a loss is made at once. Each one that fails pushes the next out by 250 ms doubling to 8 s, and there is no state in which the attempts stop.
- Off is `WgpuBackend::turn_off` and `turn_on`, for the host. Nothing in the backend turns itself off. A policy that turns it off automatically is the host's (C5) to apply through those calls.
- A lost device's pools are let go when the link replaces it: its readback buffers, its scratch and its pipelines. Its key is never used again.
- A device that was adopted can't be reopened, since the backend has nothing to open it from. Its loss is an error that says so.
- An upload step finds the new device on its next run. A readback's input says which device it is on.
- The driver's lost callback marks the device lost and records the driver's message. wgpu also calls it when a device is dropped, which isn't a loss and is ignored.
- A merged region that fails reports its covers and doesn't unmerge, as the brief says. Naming the one failing node inside a submit that the driver rejected isn't possible from the driver's message, so `at` is set only for failures found while recording.
