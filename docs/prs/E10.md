## Build

- Device identity: each device has a device key, and each (device key, memory kind) pair is one memory space id that E2 and E9 register under.
- One device per process by default (E1). Two devices exist only when the Host or an author names them, by vendor or by index. Each has its own caches, and dropping one clears only its entries.
- Cross-device handoff: a value on device A that a node on device B reads has no transfer unless a backend lists one. Planning then fails and names the ports and the spaces, as the design's transfer rule requires. Nothing copies silently.
- Dropped: the CUDA backend (dev crates/gpu/src/cuda/*, gpu-cuda), SharedValue, SharedBuffer and SharedSemaphore (interop.rs, interop/shared_value.rs), and the CUDA graph handoff. Reason: CUDA is a vendor runtime, the design lists no CUDA backend, and dev's own accelerator doc says drivers are ours, not vendor runtimes. The opaque-fd export of wgpu memory existed only for CUDA and goes with it.
- Repeated backend creation registers fresh device cache keys (dev test repeated_wgpu_backend_creation_registers_fresh_device_cache_keys).

## Proof

CI, sim backend (A11) with two spaces and no transfer: planning fails and the error names the two ports and both spaces (new). shared_context_opens_one_device_per_process (ported). repeated_wgpu_backend_creation_registers_fresh_device_cache_keys (ported). On lavapipe, two adapters if the ICD offers two: a value from one device fed to the other fails to plan. If only one adapter exists, the test skips with the reason.

## Status

Done. Run here on hardware and on lavapipe. The two devices are the best adapter and the next one where the machine has two, and the one adapter opened twice where it has one, which is the case on lavapipe. Which of the two happened on this machine isn't recorded by the test.

Differences from the brief:

- **A value does cross from one device to another, through the host, and the brief says it must fail to plan.** Each device lists a readback, a map and an upload, and the brief's own rule is that a value has no transfer unless a backend lists one. With those listed, the planner finds `readback`, `map`, `upload` and puts all three in the plan, where they are seen and costed. Nothing goes from one device to another in one hop, and no backend lists such a move: a test asserts it over both tables. Planning fails, naming the port and both spaces, where there is no way to the host, which is the case for a texture: the test feeds a camera image that imports on the default device to a node on the other. Making every crossing fail would mean hiding the upload from values that came off another device, which the planner's rule has no way to say.
- The last leg is the upload. Given a buffer on another device, in memory the host reads, it copies the bytes into a buffer of its own device and counts it as the upload it is. Given a buffer already on its device it passes it along, as before.
- A second device is `WgpuBackend::open_named(name, options)`. It is the backend `wgpu.<name>` to the planner, with spaces `wgpu.<name>.buffer` and so on and transfers `wgpu.<name>.upload` and so on, so a (device, memory kind) pair is one space id. `WgpuBackend::open` is the default device, whose ids are unchanged. Which adapter is the options' vendor, adapter name, or the new `index`, counted over the adapters that pass the rest, best first.
- **At most three named devices are alive at once** (`devices::MAX_NAMED`). A transfer's maker is a plain function with no state, so which device an upload is for is in its type, one function per place. A name is free again when its backend is dropped. Lifting the limit means a transfer's maker carrying state, which is a change to `core/backend`.
- The space id is per name, not per device key. A device opened in place of a lost one has a new key (`WgpuBackend::device_key`, `Storage::device_key`) and the same spaces, so a plan survives the loss. A buffer of the old device is refused by its key where it is bound.
- `handoff::on_device`, `device_of` and `crosses_devices` say whose a space is. `Storage::space` still answers with the kind (`wgpu.buffer`), for any device.
- `dmabuf::import_transfer_on(&backend, ..)` is the import onto a named device's texture space.
- The planning test runs against a stand-in that tells the planner exactly what the real backends tell it (id, memory, transfers), because the real backend takes only shader bodies and the test's nodes have none.
- `shared_context_opens_one_device_per_process` was already ported in E1. The sim test of a failed plan that names the port and both spaces is B9's `no_path_names_port_and_spaces`: the error names the reading port, not two ports.
- CUDA, `SharedValue`, `SharedBuffer`, `SharedSemaphore` and the opaque-fd export aren't here, as the brief settles.
