## Build

- Three memory spaces the planner can name, each with an id: device-local storage (`GpuStorage::new`, `new_uninit`), host-mapped (`new_host_mapped`, for unified memory: V3D, Mali, integrated GPUs and lavapipe), and host-cached readback (`new_host_cached`). Host-cached without a dma-heap falls back to host-mapped. E9 adds the dma-heap space to this table.
- `new_uninit` skips wgpu's lazy zero-init. Use it only for buffers the producer fully writes first (dev gpu-nodes.md: 2.3 ms against 0.47 ms for 16 MiB on V3D).
- Buffers and textures are created at load or setup, not while a region runs. Growing a buffer (dev `ensure_size`) is a load-time action. A run that needs more than the buffer holds returns a Fault, and never allocates.
- Memory hints (dev memory_hints.rs:9-61): Auto uses MemoryUsage on integrated, virtual and CPU adapters and Performance on discrete ones. The hint is an option the Host passes in. The backend does not read the environment (`DAEDALUS_GPU_MEMORY_HINTS` moves to the Host's settings, C10).
- Textures: formats the backend supports are r8, rgba8, r32f, rg32f, r8uint, rgba16uint and rg32uint, with the row-pitch and size validation of dev lib.rs:500-660 (`format_bytes_per_texel`, `validate_texture_bytes`). Each format is a Rust enum with an explicit wgpu mapping.
- Pools (dev storage_pool.rs, pool.rs): a size-classed pool with a cap and stats for scratch buffers, and a temp pool keyed by device. Pools are filled at load. A give beyond the cap drops the buffer and counts the drop. Nothing grows while a region runs.
- Staging (dev staging.rs): 16 size classes, 2 buffers per class, 64 MiB total. A readback reuses a staging buffer only within size..=2*size, so a small readback never maps a much larger buffer. Host settings may change the counts (`DAEDALUS_WGPU_STAGING_*` moves to Host settings), and zero counts normalise to one.
- Copy limiter (dev copy_limiter.rs, capabilities.rs max_inflight_copies = 8): at most 8 copies in flight, with waker support for the async path.
- Dropped: GpuState<T> (dev gpu_state.rs, a Pod state with its own pool). Node state belongs to C9, and a GPU buffer kept in state is a GpuStorage. Dropped: convert.rs's DeviceBridge, Compute and Backing wrappers, which the memory spaces replace.
- Each buffer knows its device key. Dropping the device clears its pools (dev clear_temp_pool_for_device and friends) so a lost device leaves nothing behind (E11 uses this).

## Status

Done, and run here on hardware. lavapipe runs it in the GPU lane of CI. The V3D timings are written in `testing/board-runs/E2.md` and haven't been taken.

Differences from the brief:

- The host-mapped and uncleared buffers come from `backends/vk-sys` (E13), which landed first for that reason. Off Vulkan they fall back to a plain zeroed buffer, and `Storage::is_host_mapped` says so.
- Host-cached memory falls back to host-mapped. The dma-heap fallback waits for E9.
- `uninit_storage_takes_kernel_output` writes the whole buffer from the host and reads it back, since no shader can run before E4.
- `StoragePool::take` never makes a buffer. The pool is filled with `fill` at load, and a take from an empty class returns `None` and counts a miss.
- Readbacks block until the copy is done (`Storage::read_into`). The readback that can be polled, and the async use of the copy limiter, come with E8's fences.
- The scratch pool of buffers and textures belongs to its device's context and not to a process-wide table keyed by device, so it goes with the device. Storage pools have `clear` and `device_key` for E11.
- A texture has `new` and its checks. Uploads and readbacks of textures come with the transfers in E3.
- The row-pitch check is that a row holds its pixels and is a whole number of pixels. wgpu's own 256-byte row alignment for buffer copies is applied where a copy is made, in E3.
- Memory hints, staging limits and scratch pool limits are fields of `Options`. Nothing reads the environment.
