## Build

- One benchmark comparing three ways of passing a large value along a chain: a handle to a buffer owned elsewhere (A5, A14), shared bytes, and a plain `Vec<u8>`. dev's commit 36d2af6 has the same three paths.
- It defines its own value type in the benchmark crate. Nothing about the type is known to the core.
- Each path runs the same chain of N stages, built once. The measured part is the steady-state tick.
- Counts per tick: instructions (through the I2 harness) and allocations. The handle and shared bytes must allocate zero in steady state. `Vec<u8>` is expected to allocate, and the count is recorded as the contrast.
- A case with one consumer per value and a case with fan-out, to prove that a value with one consumer touches no reference count.
- Criterion timings are for board runs only.

## Status

Done for the counted rows, with one of the brief's requirements not met by the code it measures. The board run is in `testing/board-runs/I3.md`, untested.

**A value handed on through a chain allocates once a stage. The brief requires zero for the handle and for shared bytes.** A CPU node that takes a value and returns it has the result put behind a new handle each time, so eight stages allocate eight times a tick, for both. The bytes are never copied and the shared bytes' count is never raised. This is the cost I2 found for struct outputs, and it is in the CPU backend, not in this benchmark: closing it needs a node that can take and return the handle itself. The rows hold it at 8, and `a_value_handed_on_allocates_once_a_stage_today` fails when it falls.

Measured, a tick, here:

| Path | Read by 8 nodes: allocations | Handed on through 8 stages: allocations | copies of the bytes | Read: `Ir` | Handed on: `Ir` |
|---|---|---|---|---|---|
| handle (a struct that owns its bytes) | 0 | 8 | 0 | 9,121 | 11,721 |
| shared bytes | 0 | 8 | 0 | 9,163 | 12,689 |
| `Vec<u8>` (each stage makes its own) | 0 | 16 | 8 | 9,121 | 17,420 |

Differences from the brief:

- **Two shapes, not one chain.** `read` is the host's value read through a reference by 8 nodes, which is the fan-out case and costs nothing on every path. `chain` is the value taken and handed on by 8 stages. `handle_steady_state_allocates_nothing` and `shared_bytes_steady_state_allocates_nothing` are the `read` shape, where the names are true.
- **"A handle to a buffer owned elsewhere" is a struct that owns its bytes, passed by its handle**, not A14's `ForeignRef`: a CPU node has no parameter that takes one.
- **`one_consumer_touches_no_reference_count` counts the value's own `Clone`**, which is where a second holder of the bytes would come from, and finds none along a chain. The runner's count on the handle around a value can't be seen from outside the runner. The same test shows what stands behind it: two nodes that each take one value are refused by the planner (`CopyMissing`, naming the port) before anything runs.
- The rows are in `testing/budgets/budgets.toml` and run by `scripts/ci.sh budgets` through the I2 harness, which depends on this crate and has a `handoff` command. Dev has no callgrind figure for these, so an instruction row's limit is this branch plus 10%.
- The instruction rows pass a 4 KiB value, and a chain row is fed a new one each tick, since its stages take it: making the value is in that count, for every path alike. The allocation rows pass a megabyte and count only the tick.
- The timings are in the harness's criterion bench (`handoff_*`), for the board run. Nothing here is a time.

### Added after: a value handed on by its handle (`C-handle`)

The shortfall above is closed for a node that hands a value on. A CPU node can take `Arc<T>` and return it: the port's type is `T`, the handle goes into the next cell as it is, and nothing is allocated or copied. The `handed` rows measure it: 8 stages, 0 allocations a tick, on all three paths. A node that takes `T` itself and returns one still has the result put behind a new handle, which is what the `chain` rows go on holding at 8, and that is no longer a miss: taking a value out of its handle is asking for it.

Two stages still can't each take one value, by handle or not: the planner refuses it. Stages that share a value read it through `&T`.
