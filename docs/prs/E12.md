## Build

- The lavapipe lane: the wgpu backend's conformance cases, the A12 suite cases for the backend, and the ported tests from E1-E8 and E16 run with VK_ICD_FILENAMES pointing at lavapipe. The lane fails if it runs zero GPU tests. Dev's rule that unit tests skip without an adapter stays, but a lane that skips everything is a failure.
- Validation layer on lavapipe: any validation message outside a short known list fails the lane. Dev's list (ci.sh around line 496) pins RADV, and CI has no RADV, so the list is redone for lavapipe.
- Budgets counted in CI, not timed: queue submits per region, pipelines created per merged chain, passes per region, allocations per Step after warm-up, transfers per boundary. Each is a constant in the budget crate, and a regression fails the test.
- Timed budgets run on the CM5 (board_run). The table from design.md is recorded per PR. A PR that makes a number worse says so in its description.
- gpu_bench moves into testing/crates/gpu-budgets as the measurement tool (sections batching, allocation, dispatch-floor, readback, limits). It runs on boards, not in the gate.
- Ownership of ci.sh: the lane is one function in scripts/ci.sh, which A2 owns. This PR adds scripts/gpu-lavapipe.sh and asks A2 to call it from the gate. It does not edit ci.sh.

## Status

Done for the lane, the conformance cases and the counted budgets. Run here on hardware (RADV) and on lavapipe. **The validation layer isn't installed on the machine this was written on**, so the validation half of the lane ran only on GitHub, from a trial branch that is deleted. The CM5 timings are written in `testing/board-runs/E12.md` and haven't been taken.

Differences from the brief:

- **The backend rule that a warm step allocates nothing fails on this backend, and the lane says so instead of hiding it.** wgpu allocates for every encoder, pass and submit: a region's step makes about 22 allocations and 10 more for each pass. `the_backend_rules_hold` runs the other ten rules of the A12 suite, and `a_warm_step_allocates_within_its_budget_and_not_yet_nothing` runs the eleventh, expects it to fail, and holds what it fails by to the budget. When wgpu stops allocating, that test fails and tells whoever sees it to move the rule into the list. The design's "steady-state running allocates nothing" is not met on the GPU.
- The allocation budget is a ceiling, `ALLOCATIONS_PER_STEP` (24) plus `ALLOCATIONS_PER_PASS` (10) a pass, because the count moves by one or two between runs. A test checks the ceiling hasn't gone slack by more than 4. The other budgets are exact, and fewer than the budget fails too, so a constant is lowered in the PR that earns it.
- Counted budgets, each a constant in `daedalus-gpu-budgets`: submits per region 1, passes per whole-shader node 1, passes and pipelines per merged chain 1, pipelines built by a run 0, uploads and downloads per boundary 1 each, transfers by a region 0. They are the same on RADV and on lavapipe.
- The planted region that submits twice is two things: a measurement written by hand with two submits, and two real runs of a step added together. Both fail the submit budget. A region that really splits its work can't be built without changing the backend.
- **The planted validation error is a planted log line**, checked by `scripts/gpu-lavapipe.sh --self-test`, which CI runs before the lane. A real invalid Vulkan call would need `unsafe` in a test crate. The lane also fails if the layer is asked for and writes no log, so a layer that isn't loaded can't pass as clean.
- "Fails if it runs zero GPU tests" is `DAEDALUS_GPU_REQUIRED=1`, where no adapter fails each test, together with a count of passed tests from cargo's output and a check that the device that opened is lavapipe.
- `scripts/gpu-lavapipe.known` is the list of accepted validation messages. It is empty: the lane's run on GitHub, on lavapipe under the layer, passed 147 tests and the layer's log held no error or warning. Dev's list was for RADV and isn't carried. **That the layer's log would hold a real error hasn't been shown**: the layer loaded and wrote its log file, but no real invalid call was made to see one land there.
- The GPU workflow (`.github/workflows/ci-gpu.yml`) now runs this script in place of `scripts/gpu.sh`, with the validation layer installed and required. `scripts/ci.sh` isn't edited. `scripts/gpu.sh` stays for running against a real adapter.
- The conformance crate's kernel cases check a pass an op, seven ops in one submit, and the reference's bytes at one size each. The exhaustive comparison stays in `backends/wgpu/tests/kernels.rs`, which the lane also runs.
- `gpu-budgets` the tool has the sections `limits`, `batching`, `allocation`, `dispatch-floor` and `readback`. Dev's `startup` and `images` sections aren't ported. It isn't in the gate.
- Measured here with the tool on an RX 6800 XT, for the record and not as a board run: one pass, submitted and waited for, about 0.2 ms; a region of 1, 2, 4 and 8 shader nodes allocates 32, 43, 62 and 102 times in a warm run.

### Added after: the batching section is dev's workload (`batching-match`)

`gpu-budgets batching` now times what the design's row was measured on: eight 64 KiB shader copies, as eight submits waited for once and as one submit, the median of 35 frames. It timed eight hex-encode ops with a wait after each before, which is why its first CM5 figure was far from dev's. `testing/board-runs/E12.md` has both.

### Added after: the budgets count shader runs (`one-pass`)

A region of shader nodes is one pass now, so the counted budgets are: submits per region 1, passes per region 1, shader runs per whole-shader node 1, shader runs per merged chain 1. The allocation ceiling is 32 a step and 2 a shader run, where it was 24 and 10 a pass: the base is the same work, counted with its first run.

### Added after: a region of shaders allocates nothing (`raw-region`)

The backend rule that a warm step allocates nothing now passes, and `steps_do_not_allocate` is in `the_backend_rules_hold` with the other ten. `ALLOCATIONS_PER_STEP` is 0, and the per-dispatch and slack constants are gone.

A region whose nodes are all shaders that bind storage and uniform buffers no longer goes through wgpu's encoder on Vulkan. `daedalus-vk-sys` has a `chain`: pipelines built from the same WGSL (translated by naga with the bounds checks wgpu uses, the binding table read from the shader), descriptor sets remembered by the buffers they bind, and one command buffer recorded again each run and submitted under the device's submit lock. The region's fence names the chain's place, so making one allocates nothing and one that is never polled leaves nothing behind.

What still goes through the encoder, and allocates as before: a run that is given a texture or draws to one, a region with a recording body, and every region off Vulkan. The kernel ops (`Kernels::run`, `Batch`) are not regions and also still go through it: 32 allocations for one op, 42 for eight in a batch.

Two things changed for it. A buffer made by `Storage::new` is cleared when it is made, with a submit, and not when wgpu first uses it: wgpu would otherwise clear it after a chain had written it. Bytes given to the queue to write are sent before a chain's submit.

Measured with the tool: a region of 1, 2, 4 and 8 shader nodes, and a merged chain of 4 pixel bodies, each allocate 0 times in a warm run, on an RX 6800 XT, on lavapipe and on the CM5.

### Added after: the lane is shown a real validation error (`validation-proof`)

After its clean check the lane runs one test in `daedalus-vk-sys` that makes an invalid Vulkan call on purpose, a buffer of size zero, with the layer's log sent to a file, and fails unless the log names the rule the call breaks (`VUID-VkBufferCreateInfo-size-00912`). The test does nothing unless `DAEDALUS_PLANT_VALIDATION_ERROR=1` is set. So "that the layer's log would hold a real error hasn't been shown", above, no longer stands: on GitHub's runner the lane prints that the planted call was caught.
