## Build

- This is the only crate that calls Vulkan or wgpu-hal's unsafe API directly. Each unsafe block has a SAFETY comment. Calls: the handles from wgpu-hal (`as_hal`), create_device_from_hal for the dma-buf-capable device (dev dmabuf/vulkan.rs), vkGetMemoryFdPropertiesKHR, memory import from an fd (E14 uses it), vkImportSemaphoreFd for a sync fd, and command buffer recording with submit through the raw queue.
- The crate does not own the submit lock. E1's lock is passed in as a guard, so every raw submit holds it (dev submit_lock.rs contract).
- Creating an instance or device here happens only under the driver lock from E1. The allow-list in scripts/check-gpu-driver-lock.sh names this crate's device.rs, which E1 already lists.
- Kept from dev: the detection of storage_buffer_8bit and timestamp_valid_bits and timestamp_period_ns (raw_vulkan.rs).
- Dropped: the export of an opaque fd from wgpu memory (SharedBuffer, dev interop.rs), which existed only for CUDA (E10).
- The crate exposes no raw handles to plugins or to other crates. E7's safe wrapper is the only way in.
- Settled: `WgpuBackend::adopt` (E1) goes through this crate's `from_hal` path. Its unsafe stays here.

## Status

Done. The tests run on this machine's best adapter and on llvmpipe, and all pass on both. The V3D run is written in `testing/board-runs/E13.md` and waits for E14.

Differences from the brief:

- The crate is Linux only. On other systems it has just the two lock types, and `backends/wgpu` opens a plain device.
- E1 had no submit lock. This PR adds the type (`SubmitLock`) here and gives each open device one in `backends/wgpu`. The driver lock is passed in as `&impl DriverHeld`, a marker trait that `backends/wgpu`'s guard implements.
- `backends/wgpu` now opens its device through `device::open_extended`, so a device gets dma-buf import and 8-bit storage where the adapter has them, and falls back to a plain device.
- `device::adopt_hal` is the `from_hal` path: it turns a device opened through wgpu-hal into a wgpu device, which `WgpuBackend::adopt` then takes. Nothing in this repo calls it yet.
- No raw handle leaves the crate except inside the recording closure of `Submitter::submit` and from `memory::handle`, which a recording needs to name a buffer. E7 wraps both.
- `Ticket::wait` takes a timeout. The submit ring still waits without a bound for its own slot to come free, which is dev's behaviour; E8 owns bounded waits.
- The tests are unit tests inside the crate, since they need raw calls and a device, and the backend's device doesn't leave `backends/wgpu`. `device.rs` has a test-only device constructor for them. `scripts/gpu.sh` runs them in the GPU lane.
- The dma-buf test gives `/dev/zero` as the fd: lavapipe answers with the typed `NoDmaBufImport`, and a device that can import refuses the fd. A real dma-buf import isn't tested here; E9 and E14 bring one.
- The planted-unsafe check is A2's and already runs in the gate.

### Added after: what a device needs behind an imported buffer (`V3D-import`)

Found on the CM5. `memory::import_dma_buf` allocated the memory at the size the driver reports for the buffer, which on V3D is more than the buffer's bytes, so a dma-buf of the buffer's own size was refused with `ERROR_INVALID_EXTERNAL_HANDLE`. `memory::dma_buf_bytes_needed(device, size)` says what a device needs for a buffer of `size`, `dma_buf_size_that_fits(device, have)` gives the largest buffer a dma-buf of `have` bytes can back, and `import_dma_buf` takes the dma-buf's length and refuses a short one with `Error::TooSmall { have, need }` before the driver is asked. A driver refusal of the fd is `Error::Fd`.
