## Build

- Publish `import_external(&ExternalImage) -> Texture` on the backend. `ExternalImage` is plain data the caller fills in: fds, plane offsets and strides, width, height, fourcc, modifier, acquire fence, and a stable identity for the import cache. It imports with no copy. The backend knows nothing about whose memory it is or what type it came from. Identity is the dma-sys identity (E9). The import goes through E13's memory import.
- Pure checks run first, and they are the same for every device: fourcc, stride and plane count. A tiled modifier takes aux planes (dev external/linux.rs:224). Tiled NV12 on V3D is one memory plane. Each check is a function with tests.
- Formats: NV12 imports as one sample-only image with two planes. YU12 is refused as one image (dev external/linux.rs:240). YCbCr to RGB is not in this PR.
- Padding: V3D needs 256 bytes past the last plane. NVIDIA pads NV12 to 128 KiB (64 KiB per plane). The import checks the required length and refuses with the size it needs. It never clamps.
- Refused imports (refused.rs): NVIDIA 595.104.02 closes a refused fd inside vkAllocateMemory (commit bc92027). A second close aborts in debug and hits a reused fd in release. The guard settles the fd exactly once. A refusal returns a typed error with the driver's reason, so tests can skip with it.
- Acquire fence (fence.rs): the producer's implicit write fence, or a sync_file, is waited before the GPU reads. SyncFd is the only mode: import the sync_file as a semaphore (E13) when the device supports it, else a bounded CPU wait (dev acquire-fence default of 1 s). Dropped: the Timeline mode and the watcher (E9).
- A linear dma-buf is refused on V3D with a reason, since V3D does not sample LINEAR (dev support.rs:100-103).
- Mesa and NVIDIA differ in fence timing (dev fences.rs:290-319). The fence code keeps both paths and tests both on the boards that have them.
- Settled: `backends/wgpu-author` has a trait `ImportExternal { fn describe(&self) -> ExternalImage; }` and a helper that registers the transfer for any type implementing it, so a type's owner writes only `describe`.
- Settled: imports are cached by the caller's identity, so only the first sight of a buffer pays for the import.

## Status

Done. The imports ran here for real, on RADV with dma-bufs from the system heap: an RGBA image and an NV12 image import with no copy, a host write made after the import shows through the same texture, both NV12 planes hold the host's bytes when sampled, and a real fence exported from the buffer goes through the import. lavapipe can't import, so in CI the pure tests run and the import tests stop at the typed refusal. The V3D runs are written in `testing/board-runs/E14.md` and haven't happened, and the NVIDIA rules here are from dev's notes and are tested only as arithmetic.

Differences from the brief:

- `WgpuBackend::import_external(ExternalImage) -> Arc<Texture>` takes the description by value, since it holds the fds. The texture is this backend's own `Texture`, so anything that takes one takes an import. An NV12 import is its Y plane as one channel, and `Texture::chroma` is the UV plane as two channels at half the size. `Format` gained `Rg8` and `Bgra8` for what imports as them.
- The raw Vulkan import is `daedalus_vk_sys::image::import_image`, in the crate where `unsafe` lives, and not `memory::import_dma_buf`, which makes a buffer. It creates the image with the producer's exact plane layout under the modifier, imports each dma-buf as its memory, and submits one acquire of its own: from a foreign queue family, in the general layout producers outside Vulkan leave an image in, to this device's queue as a read-only image. The producer's fence, when the device takes sync_files, is waited on by that submit.
- **The image isn't released back to the foreign queue family when the texture is dropped**, as dev does. Nothing in this repository hands a buffer on to another Vulkan user, and a producer outside Vulkan doesn't see queue families. A consumer that does needs it added.
- An import has no usage beyond sampling and copying out. Writing into a producer's buffer (dev's `UPLOAD`, `STORAGE`, `RENDER_TARGET`) isn't carried.
- The cache is by the dma-buf's identity from `dma-sys` together with how it was described, per device, and holds 16 imports. `import_stats` counts hits, imports and evictions. A cached import whose new frame comes with a pending fence has the host wait for it, since the image is already this device's.
- **Holding the producer's buffer is crude until E15.** The import's transfer step keeps the last four values it imported alive, so a producer doesn't reuse a buffer the device is still reading. E15 replaces that with a hold that ends when the reading work does. `ExternalImage` has no keepalive field for the same reason.
- `ImportExternal` and `import_transfer` are in `daedalus_wgpu::dmabuf`, not in `backends/wgpu-author`: that crate is a proc-macro crate and can't export a trait. A type's owner writes `describe` and adds `import_transfer::<T>(id, from)` to what their backend offers. Imports land in a new memory space, `wgpu.texture`.
- The checks that are the same on every device are `Described::validate`, on a description with no fds, so they are tested with none. What each driver adds is `Importer`: V3D's 256 bytes past the last plane, NVIDIA's 64 KiB a plane for NV12, and V3D's refusal of a linear image. A dma-buf shorter than the device needs is refused with the size, and never read short.
- A refused fd is settled once through a guard that either closes it or, on a driver that already closed it, forgets it. The driver is identified in `vk-sys` and the rule is tested as logic: no NVIDIA refusal happened here.
- Only the sync-fd wait and the host's bounded wait exist. A fence that isn't a sync_file never reaches a driver: `SyncFence::from_fd` refuses it first.
- YCbCr to RGB isn't done. NV12's planes are sampled as stored.
