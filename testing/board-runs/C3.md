# Board run: C3 host IO (feed, step, take)

Status: run on CM5 2026-11-10 (round trip and idle step taken with `cpu-timings`; the dev figure is not in the log).

## Check

- Form: `Steps`. Plan: one pass-through body (moves input slot 0 to output slot 1), as
  `core/host/tests/host_io.rs` `Pass` does.
- Measure one scalar payload's round trip: `feed` a static value, `step`, `take` it back, in a
  loop. Report the median per round trip.
- Compare with the dev host path timing in `docs/benchmarks-log.md`.

## Record

- Round trip, CM5, next and dev, in ns.
- Idle `step` with nothing fed, CM5, next and dev, in ns.
- Any regression needs a reason in the PR.

## Build

Build on NVMe only, never on the Github HDD. Use `CARGO_TARGET_DIR` on `/mnt/nvme-wd`.

## Result


Run on 2026-11-10 on the CM5 (raze2): OS image 2026.2.0-dev.993+e1097ec7, kernel 7.2.9-v8-16k, aarch64. Tested commit: `next` at bdbfe947.

- `core/host` tests built with `cargo test --release --no-run --target aarch64-unknown-linux-gnu -p daedalus-host` and run on the board as `host_io --nocapture --test-threads=1`: 9 of 9 pass. That includes `a_steady_feed_step_take_loop_allocates_nothing_after_warm_up`, the allocation half of this check, and `three_values_go_through_in_order`, which is the feed/step/take path.
- Not run: the median round trip for a scalar feed, step and take, and the idle `step` time, in ns, on CM5 and `dev`. This branch has no timing harness for host IO, and writing one is new code, so it was not written. The `dev` host path timing was not compared.

## Timings (cpu-timings, 2026-11-10)

Board: CM5 (raze2), kernel 7.2.9-v8-16k, aarch64, 4 cores, CPU governor `performance`. Built on
NVMe with `CARGO_TARGET_AARCH64_UNKNOWN_LINUX_GNU_LINKER` and `CC_aarch64_unknown_linux_gnu` set to
`/mnt/nvme-wd/scratch/zigcc/aarch64-cc`, as `cargo build --release --target aarch64-unknown-linux-gnu -p
daedalus-cpu-timings`. Copied to a directory of mine under `/tmp` on the board, run there, and removed
afterwards. Each section prints the median of 101 batches of 1,000 calls, after 20 warm batches; the
times are per call, in ns.

Commands: `daedalus-cpu-timings host_round_trip` and `daedalus-cpu-timings host_idle_step`, three
runs each, in one session. The round trip is `feed_inline`, `step` and `take_copy` of one `i64`
through a planned CPU pass-through node (`host.x -> timings.pass -> host.out`), which is the one
body the procedure asks for.

| Round trip, feed, step, take, ns | 371.2 | 371.1 | 376.7 | 371.2 |
| Idle step with nothing fed, ns | 28.1 | 28.9 | 28.1 | 28.1 |

## Reference: dev's host round trip on the same board (2026-11-11)

Dev's `host_graph_round_trip/push_tick_take` in `crates/engine/benches/host_graph_drive.rs` is one
scalar push, a tick and a take: the procedure's round trip, on dev's host. Built from dev at
`96747965`: `cargo bench --locked -p daedalus-engine --features plugins --bench host_graph_drive
--target aarch64-unknown-linux-gnu --no-run`. Run three times on the CM5 as `./host_graph_drive --bench
host_graph_round_trip/push_tick_take`. Criterion's median per round trip, default metrics:

| Row | run 1 | run 2 | run 3 | median |
|---|---|---|---|---|
| dev round trip, default metrics, ns | 2,400 | 2,420 | 2,410 | 2,410 |
| next round trip, `feed_inline`, `step`, `take_copy`, ns | 371.2 | 371.1 | 376.7 | 371.2 |

Next is about 6.5 times below dev. Criterion ran dev's metrics-off variant too (2,080 to 2,120 ns),
which is not the procedure's row. The workloads are close but not equal: dev's graph carries a
payload type and its engine's per-tick metrics, and ours is a CPU pass-through node. Recorded, not
read as a like-for-like speedup. Dev's idle step was not measured; the idle-step row stays
without a reference.
