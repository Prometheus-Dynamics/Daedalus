## Result, 2026-11-20

Run on 2026-11-20 on the CM5 (raze2, serial a317bcbee5226d57) in the batched session, at `next` 0d5760f8: OS image 2026.2.0-dev.993+e1097ec7, kernel 7.2.9-v8-16k, V3D 7.1.10.2. The commands, ranges and rules are in `run-sheet.md`; `scripts/board/judge.py figures` judged the results.

Judge: FAIL. The rule's validation parts hold, and every step exited 139 (SIGSEGV):

- The planted call was named: `VUID-VkBufferCreateInfo-size-00912` ("pCreateInfo->size is zero").
- The four clean runs printed no validation line: `vk-sys.lib` 23 of 23 pass, the wgpu fragment tests
  5 of 5, the region tests 9 of 9, and `raw-submit fragment-pass` timed (fragment pass 1.020 ms, raw
  chain submit 0.0845 ms against wgpu's 0.1168 ms).
- Each step printed its test result and then exited 139, at process exit, with the layer loaded.

A diagnosis in the same session (`vk-sys.lib tests::a_device_reports_what_it_was_opened_with`):

| Run | Exit |
| --- | --- |
| no layer | 0 |
| the layer, no Vulkan instance made (an `adapters::` test) | 0 |
| the layer and a device | 139, after `test result: ok` |

`LD_DEBUG=files` shows the loader closing the layer and the driver when the instance goes, each
`fini` running, and the crash after the test harness has finished: a destructor the layer registered
runs after the layer is unmapped. The layer was built with zig's static libc++
(`run-sheet.md`, "What the board needs"), so the cause is in that build, not in the code under test.
The fix is on the host, and E13 runs again in the next board session.

## Result, 2026-11-20, second session

Raze #2, image 993, `next` 2650b768, the layer linked with `-z nodelete` (`run-sheet.md`). Only E13,
E9 and E14 ran (`BATCH_FIGURES="e9 e14"`).

- The planted call was named: `VUID-VkBufferCreateInfo-size-00912`. No step exited 139: the layer
  build was the cause of the earlier crash, as diagnosed.
- `vk-sys.lib` (25 of 25 pass) printed 12 validation lines, all from code new in #321:
  - `VUID-vkDestroySemaphore-semaphore-05149` (4): `signal_sync_fd` destroyed its semaphore while
    the submit that signalled it could still be running.
  - `VUID-vkCmdWaitEvents-srcStageMask-01158` and `VUID-vkSetEvent-event-09543` (4 each): the test
    gate set an event from the host while a `vkCmdWaitEvents` waited on it, which Vulkan forbids.
- The wgpu fragment (5 of 5) and region (9 of 9) tests and `raw-submit fragment-pass` printed none.

Fixed on the host: a pooled `SyncFdSignal` uses a semaphore again, or destroys it, only once its
submit's fence has signalled, and the gate waits on a timeline semaphore the host signals. The x86
build of the same layer on lavapipe names the same three rules on the old code and nothing on the
fix. E13 runs again in the next board session.
