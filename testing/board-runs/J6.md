# Board run: J6 the dma-buf memory space, and J7 the GPU lease, on V3D

Status: run 2026-11-13 on the CM5 (raze2) at `next` c38d255d: 10 of 10 tests pass in release, with the dma-heap required.

## Check

Build from NVMe, never from the HDD.

- `cargo test --release --no-run --target aarch64-unknown-linux-gnu -p daedalus-dmabuf --test space -p daedalus-example-gpu --test dmabuf -p daedalus-wgpu --test lease`, the three binaries copied to the board and run as `DAEDALUS_GPU_REQUIRED=1 DAEDALUS_DMA_HEAP_REQUIRED=1 flock /run/lock/raze-gpu.lock ./<binary> --test-threads=1`.
- A value a CPU node makes in the `dmabuf` space reaches a shader by the import from that space, with one import and no upload counted by the device, and the shader's words are the CPU's.
- On a device planned without dma-buf import, the same value is handed to the host and uploaded: no import, one upload.
- The dma-buf test binary run 20 times over, since its first version corrupted the heap about one run in eight on the desktop.
- A lease set on the device is asked for and given back in pairs.

## A read-only dma-buf, 2026-11-13

Run on the CM5 (raze2): kernel 7.2.9-v8-16k, V3D 7.1.10.2, as root. Tested commit: `next` at 11e2d8b1, release. The wgpu crate's `readonly` unit test and `tests/every_adapter.rs`, each run under both board locks (`flock /run/lock/raze-gpu.lock flock /run/lock/board-gpu.lock`), with `DAEDALUS_GPU_REQUIRED=1 DAEDALUS_DMA_HEAP_REQUIRED=1`. No service was stopped.

- A dma-buf whose fd only allows reading is imported by V3D, and its bytes read back through the device.
- What the device then writes through the imported buffer, the host reads through its read-only mapping. A read-only fd stops a host mapping from writing; it doesn't stop a device that imported the buffer.
- The import is listed for a writable type and for a read-only one: `dma_heap` and `dma_read_only` are both true on V3D.
- On this kernel the heap gives a read-only fd when asked for one at allocation, a PROT_READ mapping and the read sync work on it, a writable mapping is refused, and opening the buffer again through `/proc/self/fd` is refused (ENXIO).
- `every_adapter`: 2 of 2 pass, and 10 of 10 on ten more runs.

The same test on the desktop (2026-11-13, `next` at 11e2d8b1): the Radeon RX 6800 XT (RADV) imports a read-only fd and reads it back; the NVIDIA RTX 4060 refuses any dma-heap buffer, read-only or not; llvmpipe imports a writable fd and refuses a read-only one.

The board's heaps (`/dev/dma_heap/system`, `linux,cma`, `default_cma_region`) are root:root 600. A process that isn't root can't open one, so its device is recorded as not importing and its dma-buf values are uploaded. This run was root's.

## A process that isn't root, 2026-11-13

Run on the CM5 (raze2): kernel 7.2.9-v8-16k, V3D 7.1.10.2. Tested commit: `next` at 227f000e with the check program `testing/crates/gpu-budgets/src/bin/nonroot_import.rs`, release. Started as root under both board locks: `flock /run/lock/raze-gpu.lock flock /run/lock/board-gpu.lock ./nonroot_import 900 28`. The root parent allocates a buffer from the system heap for each kind of fd and starts itself again as uid 900, the user the board's device service drops to, with gid 28 (`video`), the buffer on the child's standard input. No service was stopped, and no user, group or permission was changed.

- The child isn't root and can't open `/dev/dma_heap/system` (root:root 600), so nothing is tried when its device opens: the answer is unknown for both kinds of fd.
- Writable fd: unknown before, imports after, no copy, and the bytes read back are the parent's.
- Read-only fd: unknown before, imports after, no copy, and the bytes read back.
- Four runs, four passes.

So a consumer that isn't root imports a dma-buf it is handed on V3D, in place, and the first one settles what its device takes.

The same check with gid 900, the user's own group and no other, fails before any import: the driver prints `Opening /dev/dri/card1 failed: Permission denied`, and the same for `card0`, and no adapter is found. On this board `/dev/dri/renderD128` is `crw-rw-rw- root:render` and the card nodes are `crw-rw---- root:video`. V3D's Vulkan driver opens the card nodes too, so a process that isn't root has to be in `video`. The board's service user is. The driver also turns its shader cache off when it can't write under the process's home, which was root's here.

## Values at offsets in one dma-buf, and a second import, 2026-11-13

Run on the CM5 (raze2): kernel 7.2.9-v8-16k, V3D 7.1.10.2. Tested: `next` at b3916178 with the offset import, release, the check program `testing/crates/gpu-budgets/src/bin/nonroot_import.rs`. Each case four times, started as root under both board locks (`flock /run/lock/raze-gpu.lock flock /run/lock/board-gpu.lock`). No service was stopped, and no user, group or permission was changed.

`nonroot_import root` is the producer itself: one buffer from the system heap, three values of 4096 bytes at offsets 0, 8192 and 16384, each run through one import step. `nonroot_import 900 28` hands the same buffer to a child that is uid 900 with gid 28 (`video`) and can't open the heap, and repeats the two cases of the section above.

- Each of the three values is imported at its offset, in place, with no copy, and the device's bytes are the value's.
- The producer writes the buffer again: each value is found again, nothing is imported and nothing copied, and the device has the new bytes.
- A second step imports value 0 again while the first import of it is held. V3D takes it: imported in place, the right bytes from both, and from the first after the second is dropped.
- As uid 900 the writable and read-only cases are as before: unknown, then imported, no copy.
- Eight runs, eight passes, every line the same. Nothing was refused.

So on V3D several values share one dma-buf, each imported where it is, by root or by a process handed the fd, and the driver counts repeated imports of one dma-buf, which is what going past `Options::kept_imports` relies on.
