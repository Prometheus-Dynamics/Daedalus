# Board run: E11 real device loss on V3D

Status: re-run 2026-11-11 on CM5 (raze2) at `next` 6245c925: the loss test passes on V3D. The real timeout (the `grind` shader past the 5 s bound) was not induced: no harness on `next` runs it. Run again 2026-11-16 in the batched session: the ramp ran on V3D, and no wait reached the 5 s bound. The kernel reset the hung job five times and the timeout path was not reached (see the 2026-11-16 result).

## Check

Command: `DAEDALUS_GRIND_ROUNDS=<loops> DAEDALUS_GRIND_REPEAT=<repeat> cargo run --release -p daedalus-gpu-budgets -- grind`. It is opt-in and runs only when named. It prints the wait's result and time, the next run's fault, the reopen and the known run's check, and whether the abandoned work finished. `DAEDALUS_GRIND_BOUND_MS` lowers the wait bound for a test of the path only; the record's run uses the default bound.

Build from NVMe, never from the HDD.

- `DAEDALUS_GPU_REQUIRED=1 cargo test -p daedalus-wgpu --test region`: the loss test, which marks
  a live device lost, has to pass on V3D as it does elsewhere.
- Induce a real timeout: run a region whose shader loops long enough to pass the 5 s wait bound
  (the `grind` shader of `fence_tests.rs` with a large `rounds`), and wait on its ticket.
  Expect: the wait fails as a timeout, the device is marked lost, the region's next run faults,
  the backend opens a new device, and the run after that is correct.
- Record what the driver does: whether its own lost callback fires, what message it gives,
  whether the old device's work ever finishes, and how long the reopen takes.

## Result


Run on 2026-11-10 on the CM5 (raze2): OS image 2026.2.0-dev.993+e1097ec7, kernel 7.2.9-v8-16k, aarch64, 4 cores, 4 GB RAM. V3D 7.1.10.2 through the Broadcom ICD (Vulkan 1.3.354, driver 26.1.8), `/dev/dri/renderD128`. Tested commit: `next` at bdbfe947.

Method: the test binaries were built with `cargo test --release --no-run --target aarch64-unknown-linux-gnu -p <crate>` on NVMe, copied to `/tmp/daedalus-next/bin` on the board, and run as `DAEDALUS_GPU_REQUIRED=1 flock /run/lock/raze-gpu.lock ./<binary> --nocapture --test-threads=1`, with `DAEDALUS_DMA_HEAP_REQUIRED=1` where the variable is named below. Logs are on the board under `/tmp/daedalus-next/logs`.

- `wgpu-region`, `a_lost_device_faults_the_region_then_is_reopened_and_the_region_runs_again`: pass on V3D. The loss test, which marks a live device lost, passes here as it does elsewhere.
- `wgpu-lib`, `fence_tests::a_wait_that_outlives_its_bound_fails_and_marks_the_device_lost`: pass. This test drives the timeout directly through `context.timed_out`, as its own comment says. It waits on no long shader, so it is not the real timeout the procedure asks for.
- Not run: the induced real timeout (a region whose shader runs past the 5 s wait bound, waited on through its ticket, then the next run faulting and the backend reopening the device). The `grind` shader lives in `backends/wgpu/src/fence_tests.rs`, private to that module, and no runnable test drives it through a region. Writing that driver is new code, so it was not written. For that reason the driver's lost callback, its message, whether the old device's work finishes, and the reopen time are not recorded.

## Result, 2026-11-16 (batched session)

Run at `next` 748ef3cc on the CM5, one ramp. The gate read `watchdog armed: yes (RuntimeWatchdogUSec=15s)`, so
the ramp ran. The ramp stops at the first wait that fails. None failed.

- The timeout path did not run. The tool says so after each step.
- The kernel log (`dmesg-e11.txt`) has five lines `v3d ... Resetting GPU for hang`, about 0.54 s apart, from
  100651.05 s to 100653.22 s on the log's clock. The count was 0 at the start of the batch and 5 at the end
  (`gpu-health.txt`). The driver reset the hung job itself about half a second in, so the wait finished before
  its bound. The tool's message describes this case.
- After the ramp the GPU answered. `dispatch-floor` ran in 72 to 75 µs and `gpu-health.txt` ends `gpu ok`. The
  board was not rebooted.
- Not recorded, because the timeout path did not run: the failed wait, the device marked lost, the next run's
  fault, the reopen, the driver's lost callback and the reopen time.
- On V3D, with this workload, the wait's own timeout path is not reached. E11's timeout path stays proven on
  lavapipe only.
- The five `Resetting GPU for hang` lines are the ramp's own, on purpose: the ramp is built to hang the GPU. They are not a fault.
- Real device loss is still not verified on hardware. A run that could reach the wait's timeout path on V3D, not made here: `DAEDALUS_GRIND_BOUND_MS=100 DAEDALUS_GRIND_ROUNDS=10000000 DAEDALUS_GRIND_REPEAT=1 daedalus-gpu-budgets grind`, which lowers the bound below the driver's reset and marks the device lost.
