# Board run: E2 buffer allocation on V3D

Status: partly run on CM5 2026-11-10 (one storage test fails on V3D; timings not taken).

## Check

Build from NVMe, never from the HDD. Time each of these for a 16 MiB buffer, as the median of 50
after 5 warm-up allocations, dropping the buffer each time:

- `Storage::new` with `Options::hints` at `MemoryHints::MemoryUsage`, which is what `Auto` picks
  on V3D. `dev` measured 5.8 to 6.4 ms.
- `Storage::new` with `MemoryHints::Performance`. `dev` measured 0.005 ms once blocks exist.
- `Storage::new` followed by a first write, which pays wgpu's zero-fill. `dev` measured 2.3 ms.
- `Storage::new_uninit`. `dev` measured 0.47 ms.

Also run `DAEDALUS_GPU_REQUIRED=1 cargo test -p daedalus-wgpu --test storage` on the board, and
record whether host-mapped and host-cached buffers report as mapped.

## Result


Run on 2026-11-10 on the CM5 (raze2): OS image 2026.2.0-dev.993+e1097ec7, kernel 7.2.9-v8-16k, aarch64, 4 cores, 4 GB RAM. V3D 7.1.10.2 through the Broadcom ICD (Vulkan 1.3.354, driver 26.1.8), `/dev/dri/renderD128`. Tested commit: `next` at bdbfe947.

Method: the test binaries were built with `cargo test --release --no-run --target aarch64-unknown-linux-gnu -p <crate>` on NVMe, copied to `/tmp/daedalus-next/bin` on the board, and run as `DAEDALUS_GPU_REQUIRED=1 flock /run/lock/raze-gpu.lock ./<binary> --nocapture --test-threads=1`, with `DAEDALUS_DMA_HEAP_REQUIRED=1` where the variable is named below. Logs are on the board under `/tmp/daedalus-next/logs`.

- `wgpu-storage` (with `DAEDALUS_DMA_HEAP_REQUIRED=1`): 6 of 7 pass: `host_mapped_storage_round_trips_without_staging`, `staging_pool_reuses_readback_buffers_and_tracks_stats`, `storage_pool_reuses_within_its_cap`, `textures_are_made_at_setup_and_checked`, `the_backend_names_its_memory_spaces`, `uninit_storage_takes_kernel_output`.
- FAIL: `a_dma_heap_buffer_is_one_memory_for_the_host_and_the_device` at `backends/wgpu/tests/storage.rs:243:23`, message `a dma-heap buffer: Vulkan: ERROR_INVALID_EXTERNAL_HANDLE`. A dma-heap buffer cannot be made into a Vulkan storage buffer on V3D through this path. Not diagnosed further; this is a finding.
- Not run: the four allocation timings (`Storage::new` with `MemoryUsage` and with `Performance`, `Storage::new` with a first write, and `Storage::new_uninit`), each as the median of 50 for 16 MiB. This branch has no harness that times them, and writing one is new code, so it was not written. Whether host-mapped and host-cached buffers report as mapped was not checked.

## Rerun after fixes, 2026-11-10

Same board (CM5, raze2, V3D through the Broadcom ICD), release build, every test binary of the GPU crates, one thread: all pass.

- **The uniform and pixel-chain failures above were not V3D's.** `a_uniform_takes_plain_bytes_or_bytes_already_on_the_device`, `a_config_is_a_port_or_zeroes` and `a_chain_given_a_texture_draws_one` failed in any release build, on the desktop too. The tests built an input cell with `put_inline` from bytes that were gone by the time the step ran, and a debug build happened to still read them. The tests now keep the bytes for the run. The library was right.
- **The dma-heap and dma-buf storage failures above were real, and are fixed.** V3D needs more memory behind an imported buffer than the buffer has bytes, and refused a dma-buf of exactly the buffer's size with `ERROR_INVALID_EXTERNAL_HANDLE`. A dma-heap buffer is now allocated at the size the device asks for, an imported one is given a buffer that fits its dma-buf, and a dma-buf that is too short is refused with both sizes before the driver sees it. `a_dma_heap_buffer_is_one_memory_for_the_host_and_the_device` and `frames_import_once_per_dmabuf_and_read_in_place` pass on V3D.
- Still true: a linear dma-buf image isn't sampled by V3D, so no image has been imported with no copy on this board. That needs frames from the camera pipeline.
- Still true: 8 ops took 2.89 ms in one submit here, against 1.32 ms on `dev`. Not diagnosed.
