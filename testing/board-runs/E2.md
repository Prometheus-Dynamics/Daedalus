# Board run: E2 buffer allocation on V3D

Status: partly run on CM5 2026-11-10 (one storage test fails on V3D; timings not taken).

## Check

Build from NVMe, never from the HDD. Time each of these for a 16 MiB buffer, as the median of 50
after 5 warm-up allocations, dropping the buffer each time:

- `Storage::new` with `Options::hints` at `MemoryHints::MemoryUsage`, which is what `Auto` picks
  on V3D. `dev` measured 5.8 to 6.4 ms.
- `Storage::new` with `MemoryHints::Performance`. `dev` measured 0.005 ms once blocks exist.
- `Storage::new` followed by a first write, which pays wgpu's zero-fill. `dev` measured 2.3 ms.
- `Storage::new_uninit`. `dev` measured 0.47 ms.

Also run `DAEDALUS_GPU_REQUIRED=1 cargo test -p daedalus-wgpu --test storage` on the board, and
record whether host-mapped and host-cached buffers report as mapped.

## Result


Run on 2026-11-10 on the CM5 (raze2): OS image 2026.2.0-dev.993+e1097ec7, kernel 7.2.9-v8-16k, aarch64, 4 cores, 4 GB RAM. V3D 7.1.10.2 through the Broadcom ICD (Vulkan 1.3.354, driver 26.1.8), `/dev/dri/renderD128`. Tested commit: `next` at bdbfe947.

Method: the test binaries were built with `cargo test --release --no-run --target aarch64-unknown-linux-gnu -p <crate>` on NVMe, copied to `/tmp/daedalus-next/bin` on the board, and run as `DAEDALUS_GPU_REQUIRED=1 flock /run/lock/raze-gpu.lock ./<binary> --nocapture --test-threads=1`, with `DAEDALUS_DMA_HEAP_REQUIRED=1` where the variable is named below. Logs are on the board under `/tmp/daedalus-next/logs`.

- `wgpu-storage` (with `DAEDALUS_DMA_HEAP_REQUIRED=1`): 6 of 7 pass: `host_mapped_storage_round_trips_without_staging`, `staging_pool_reuses_readback_buffers_and_tracks_stats`, `storage_pool_reuses_within_its_cap`, `textures_are_made_at_setup_and_checked`, `the_backend_names_its_memory_spaces`, `uninit_storage_takes_kernel_output`.
- FAIL: `a_dma_heap_buffer_is_one_memory_for_the_host_and_the_device` at `backends/wgpu/tests/storage.rs:243:23`, message `a dma-heap buffer: Vulkan: ERROR_INVALID_EXTERNAL_HANDLE`. A dma-heap buffer cannot be made into a Vulkan storage buffer on V3D through this path. Not diagnosed further; this is a finding.
- Not run: the four allocation timings (`Storage::new` with `MemoryUsage` and with `Performance`, `Storage::new` with a first write, and `Storage::new_uninit`), each as the median of 50 for 16 MiB. This branch has no harness that times them, and writing one is new code, so it was not written. Whether host-mapped and host-cached buffers report as mapped was not checked.

## Rerun after fixes, 2026-11-10

Same board (CM5, raze2, V3D through the Broadcom ICD), release build, every test binary of the GPU crates, one thread: all pass.

- **The uniform and pixel-chain failures above were not V3D's.** `a_uniform_takes_plain_bytes_or_bytes_already_on_the_device`, `a_config_is_a_port_or_zeroes` and `a_chain_given_a_texture_draws_one` failed in any release build, on the desktop too. The tests built an input cell with `put_inline` from bytes that were gone by the time the step ran, and a debug build happened to still read them. The tests now keep the bytes for the run. The library was right.
- **The dma-heap and dma-buf storage failures above were real, and are fixed.** V3D needs more memory behind an imported buffer than the buffer has bytes, and refused a dma-buf of exactly the buffer's size with `ERROR_INVALID_EXTERNAL_HANDLE`. A dma-heap buffer is now allocated at the size the device asks for, an imported one is given a buffer that fits its dma-buf, and a dma-buf that is too short is refused with both sizes before the driver sees it. `a_dma_heap_buffer_is_one_memory_for_the_host_and_the_device` and `frames_import_once_per_dmabuf_and_read_in_place` pass on V3D.
- Still true: a linear dma-buf image isn't sampled by V3D, so no image has been imported with no copy on this board.
- Still true: 8 ops took 2.89 ms in one submit here, against 1.32 ms on `dev`. Not diagnosed.

## Timings, 2026-11-10

Built with `cargo build --release --target aarch64-unknown-linux-gnu -p daedalus-gpu-budgets` and run as `flock /run/lock/raze-gpu.lock ./daedalus-gpu-budgets <section>` on the CM5 (raze2): OS image 2026.2.0-dev.993+e1097ec7, kernel 7.2.9-v8-16k, V3D 7.1.10.2. Tested commit: `next` at a2ed64ea plus the timing sections of this PR. Each figure is a median of 50 runs after 5 warm-up runs, unless a line says otherwise. Three runs were made of each section, and the ranges below are the lowest and highest medians across them.

Storage allocation, 16 MiB, from the `alloc16` section: `Storage::new` with each memory hint, `Storage::new` followed by a first write of 16 MiB (which pays wgpu's zero-fill and then the copy), and `Storage::new_uninit`. Each is the median of 50 runs after 5 warm-up runs, dropping the buffer each time. The command is `daedalus-gpu-budgets alloc16`, three runs.

| case | CM5 | dev | meets dev? |
|---|---|---|---|
| `Storage::new`, hint MemoryUsage | 5.229 to 5.898 ms | 5.8 to 6.4 ms | yes, within dev's range |
| `Storage::new`, hint Performance | 0.001 ms | 0.005 ms once blocks exist | yes |
| `Storage::new` then a first write | MemoryUsage 20.491 to 21.446 ms; Performance 9.383 to 9.577 ms | 2.3 ms | no |
| `Storage::new_uninit` | 5.405 to 5.951 ms | 0.47 ms | no, about 12 times dev |

The first-write case in this table includes a 16 MiB host copy into the buffer, which the procedure's own wording does not spell out, so it is not certain that dev's 2.3 ms measured the same thing. ## Follow-up, 16 MiB allocation, 2026-11-10

Build: this branch (based on `origin/next` at abeffb9d). Three CM5 runs of `alloc16`:

| case | run 1 | run 2 | run 3 | dev figure |
|---|---|---|---|---|
| `Storage::new`, hint MemoryUsage | 8.322 ms | 8.997 ms | 9.353 ms | 5.8 to 6.4 ms |
| `Storage::new`, hint Performance | 0.0619 ms | 0.0582 ms | 0.0571 ms | 0.005 ms |
| `Storage::new` then a first write | 28.03 ms | 28.18 ms | 29.17 ms | 2.3 ms |
| `Storage::new_uninit` | 5.574 ms | 5.886 ms | 5.694 ms | 0.47 ms |

Against the earlier run in this file (before this branch): MemoryUsage was 5.2 to 5.9 ms and Performance was 0.0006 ms, so both moved on this base. The first-write case now includes the 16 MiB submit that the write budget makes, which the earlier figure did not. I have not established which change moved the MemoryUsage and Performance figures.

`Storage::new_uninit` is not fixed. It allocates fresh device memory for each buffer through the vk-sys placement path, and that costs about the same as a hinted `Storage::new` (5.6 to 5.9 ms against 8.3 to 9.4 ms). The reference figure of 0.47 ms is a pooled path, where a freed block is reused: the Performance hint's 0.06 ms is that path. Making `new_uninit` pooled needs a block pool for the vk-sys placement, which is a change to the memory design, so it is not done here. The simpler route, creating the buffer through wgpu without the clear, is not safe: wgpu clears a buffer it has not seen written before its first use, which would undo the writes a Vulkan-recorded chain makes first.

## Follow-up, `Storage::new_uninit` is handed out again, 2026-11-10

`Storage::new_uninit` no longer allocates device memory each time. A buffer of uncleared device memory goes back to its device when it is dropped, and the next `new_uninit` of the same size takes it, once the device has finished everything it was given. At most four are kept, 64 MiB together.

Three CM5 runs of `alloc16`, release: `Storage::new_uninit` 16 MiB is 0.0004 ms in each, where it was 5.6 to 5.9 ms and `dev` recorded 0.47 ms. The first one of a size still pays the allocation.

Still over `dev` in the same runs: `Storage::new` with the MemoryUsage hint, 8.73 to 8.77 ms against 5.8 to 6.4 (it now clears the buffer when it is made), and `Storage::new` then a first write, 27.8 ms with MemoryUsage and 4.3 to 4.8 ms with Performance against 2.3 ms.

## Follow-up, `Storage::new` is the backend's own memory, 2026-11-11

On Vulkan `Storage::new` no longer goes through wgpu's allocator and clear. The buffer is device memory the backend allocates itself, handed out again when it is let go, as `new_uninit`'s is. Until the device is first shown a new buffer the host has it to itself: where the device's memory is the host's too, as on V3D, a write goes straight into the mapped memory, and zeroes are written only where something would otherwise see what was there (a write of part of it zeroes the rest on the host; a first use by the device with nothing written clears it on the device; a write of all of it needs neither).

Three CM5 runs, release, `alloc16` and `transfers`:

| case | CM5 now | CM5 before | `dev` |
|---|---|---|---|
| `Storage::new` 16 MiB, either hint | 0.0005 ms | 8.73 to 8.77 ms (MemoryUsage), 0.065 to 0.072 ms (Performance) | 5.8 to 6.4 ms, 0.005 ms |
| `Storage::new` then a first write of 16 MiB | 3.78 to 4.56 ms | 27.8 ms, 4.3 to 4.8 ms | 2.3 ms |
| `Storage::new_uninit` 16 MiB | 0.0005 ms | 0.0004 ms | 0.47 ms |
| 16 MiB upload step to device memory | 3.29 to 3.46 ms | about 19 ms | |
| 16 MiB upload step to mapped memory | 3.32 to 3.64 ms | | |

The first buffer of a size still pays its allocation: these are medians of buffers made and dropped in a row. **The first write is still over `dev`'s 2.3 ms.** What is left of it is the copy of 16 MiB into the device's memory, which the same tool measures alone at 3.2 to 3.3 ms; whether `dev`'s figure included that copy isn't known.

Every test binary of `daedalus-vk-sys`, `daedalus-wgpu`, `daedalus-gpu-budgets` and `daedalus-wgpu-conformance` passes on the board.

## Reference rerun, the device's first use of a 16 MiB buffer (reference-rerun, 2026-11-11)

What the reference's 2.3 ms measures: its `allocation` section (`crates/gpu/examples/gpu_bench/linux/alloc.rs`)
times `first_use`, a 4-byte copy submitted to a freshly made buffer nobody has written, submit to
done. wgpu clears the buffer on that first use, so the figure is the device's clear. It includes no
host copy of 16 MiB. Our `alloc16` measured `Storage::new` followed by `Storage::write` of 16 MiB,
which is a host copy, so it was never like-for-like with that figure. The like-for-like figure is
our own device first use, added to `alloc16` in this PR with the same kernel and sizes.

Built from a clone of `origin/dev` at `96747965` on NVMe, `cargo build --release --locked
--target aarch64-unknown-linux-gnu -p daedalus-gpu --features gpu-dmabuf --example gpu_bench`, copied
to the CM5, run three times as `flock /run/lock/raze-gpu.lock` with `GPU_BENCH_SECTIONS=allocation`.
Ours: `daedalus-gpu-budgets alloc16`, built from this PR, three runs, same lock.

| Row | reference, run 1 / 2 / 3 | reference median | ours, run 1 / 2 / 3 | ours median |
|---|---|---|---|---|
| 16 MiB first use, MemoryUsage hint, ms | 2.166 / 1.985 / 2.253 | 2.166 | 1.837 / 1.889 / 1.846 | 1.846 |
| 16 MiB first use, Performance hint, ms | 3.143 / 3.056 / 2.926 | 3.056 | not run | |
| 16 MiB `Storage::new` then host write, ms | not measured by the reference | | 3.762 / 3.642 / 3.865 | 3.762 |

Result: the reference's 2.3 ms (the `first_use` figure in E2's check) is the device clear, and ours is
1.85 ms on the same clear. Ours is not slower for this measurement. The host-write row has no reference
figure: it measures a different thing. The 16 MiB host copy into the buffer is what the reference's
`write in place` rows measure, 8.5 to 9.3 ms there, and it is not compared here.
