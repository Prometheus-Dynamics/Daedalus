Status: partly run on CM5 2026-11-10 (image, region and pixel tests partly fail on V3D; timings not taken).

## Check

- `DAEDALUS_GPU_REQUIRED=1 DAEDALUS_DMA_HEAP_REQUIRED=1 cargo test -p daedalus-wgpu --test image
  --test import --test region -- --nocapture`, and `cargo test -p daedalus-wgpu-author --test
  pixel`. Record any refusal with its message.
- The cost of an import that is found in the cache (`import_storage` on a buffer already
  imported). `dev` measured 16 to 29 µs per image. Record it, and `storage_import_stats`.
- The direct copy (`ImageCopy`, plan `Direct`) at 640x480 XRGB and at 1280x720. `dev` measured
  0.49 ms and 0.71 ms with the TFU, against 2.9 ms and 8.6 ms for a shader copy. A time near the
  shader's means the TFU wasn't taken: record which.

## Rerun after fixes, 2026-11-10

Same board (CM5, raze2, V3D through the Broadcom ICD), release build, every test binary of the GPU crates, one thread: all pass.

- **The uniform and pixel-chain failures above were not V3D's.** `a_uniform_takes_plain_bytes_or_bytes_already_on_the_device`, `a_config_is_a_port_or_zeroes` and `a_chain_given_a_texture_draws_one` failed in any release build, on the desktop too. The tests built an input cell with `put_inline` from bytes that were gone by the time the step ran, and a debug build happened to still read them. The tests now keep the bytes for the run. The library was right.
- **The dma-heap and dma-buf storage failures above were real, and are fixed.** V3D needs more memory behind an imported buffer than the buffer has bytes, and refused a dma-buf of exactly the buffer's size with `ERROR_INVALID_EXTERNAL_HANDLE`. A dma-heap buffer is now allocated at the size the device asks for, an imported one is given a buffer that fits its dma-buf, and a dma-buf that is too short is refused with both sizes before the driver sees it. `a_dma_heap_buffer_is_one_memory_for_the_host_and_the_device` and `frames_import_once_per_dmabuf_and_read_in_place` pass on V3D.
- Still true: a linear dma-buf image isn't sampled by V3D, so no image has been imported with no copy on this board. That needs frames from the camera pipeline.
- Still true: 8 ops took 2.89 ms in one submit here, against 1.32 ms on `dev`. Not diagnosed.

## Timings, 2026-11-10

Built with `cargo build --release --target aarch64-unknown-linux-gnu -p daedalus-gpu-budgets` and run as `flock /run/lock/raze-gpu.lock ./daedalus-gpu-budgets <section>` on the CM5 (raze2): OS image 2026.2.0-dev.993+e1097ec7, kernel 7.2.9-v8-16k, V3D 7.1.10.2. Tested commit: `next` at a2ed64ea plus the timing sections of this PR. Each figure is a median of 50 runs after 5 warm-up runs, unless a line says otherwise. Three runs were made of each section, and the ranges below are the lowest and highest medians across them.

Image copies (`ImageCopy`, `image` section), device time from `run` to its ticket done, and the import cache. The command is `daedalus-gpu-budgets images`.

| case | CM5 (3 runs) | dev figure | meets dev? |
|---|---|---|---|
| XRGB 640x480 at stride 2560, plan Direct | 0.281 to 0.337 ms | 0.49 ms with the TFU | yes (faster) |
| XRGB 1280x720 at stride 5120, plan Direct | 0.932 to 0.947 ms | 0.71 ms | no, about 1.3 times dev |
| GREY 640x480 at stride 640, plan Folded { rows: 2 } | 0.416 to 0.458 ms | 0.43 ms | yes |
| GREY 640x480 at stride 768, plan Direct | 0.265 to 0.296 ms | 0.27 ms | yes |
| GREY 640x480 at stride 644, plan Rows | 35.0 to 36.9 ms | 21 ms | no, about 1.7 times dev |
| `import_storage`, found in the cache | 1.5 us | 16 to 29 us | yes (faster) |

The shader copy that dev compares against (2.9 and 8.6 ms) was not measured on this board, so I cannot say from this run whether the TFU was taken for the XRGB copies. The two XRGB times are well under the shader figure, which suggests it was, but that is inference, not a measurement. The plan each copy takes was printed for every case.

Import refusal: a buffer of exactly the image's length is refused with `the dma-buf is 307200 bytes, and this device needs 307456 for the image`. The 256 bytes are V3D's read-past slack (`dmabuf/modifiers.rs`). The same import on the desktop AMD GPU succeeds, since the rule is V3D's.

Camera frames on this board are in E14.

Not run: the pixel chain of four fed an imported camera texture (one render pass against the compute form). The fragment form of a chain (`merge::fragment_pass`) has no harness in this PR.

## Follow-up, image copy timings, 2026-11-10

Build: this branch, based on `origin/next` at 108ed8e4. Three CM5 runs of `daedalus-gpu-budgets images`, median of 50 after 5 warm-up runs.

Row-by-row case, GREY 640x480 at stride 644 (plan `Rows`): before, one copy command per row, 35.0 to 36.9 ms against dev's 21 ms. Now one repack compute pass packs all 480 rows at a 256-aligned pitch into a staging buffer, and one copy writes the texture: 3.413 to 3.419 ms, which meets dev's 21 ms by a wide margin.

XRGB 1280x720 at stride 5120 (plan `Direct`): 0.937 to 0.962 ms against dev's 0.71 ms, so it still misses by about a third. This is where the time goes: the copy runs at about 3.9 GB/s, and the time is linear in the bytes moved (1280x360 0.482 to 0.488 ms, 960x540 0.527 to 0.558 ms, 1024x768 0.779 to 0.792 ms, 1280x720 0.937 to 0.962 ms). The same rate holds for one byte a pixel (GREY 1280x720 0.194 to 0.257 ms; GREY 2560x720 0.459 to 0.496 ms) and for XRGB 640x480 (0.320 to 0.325 ms), so the format and the width do not matter. The source memory does not matter either: from device memory 0.946 ms, from a dma-heap buffer 0.938 ms, from host-mapped memory 0.932 ms.

So the copy is bounded by the copy engine's throughput for this path. Dev's 0.71 ms is about 5.2 GB/s, which is consistent with the texture formatting unit doing the copy and this path not reaching it. I did not find a way to make wgpu's copy command take that path, and I did not measure the TFU directly. The figure stays a miss.

The other figures in the section are unchanged: XRGB 640x480 0.320 to 0.325 ms (dev 0.49, meets), folded GREY 640x480 0.426 to 0.431 ms (dev 0.43, meets), direct GREY stride 768 0.266 to 0.274 ms (dev 0.27, meets).
