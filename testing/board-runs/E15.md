# Board run: E15 images into storage and sampled textures on V3D

Status: partly run on CM5 2026-11-10 (image, region and pixel tests partly fail on V3D; timings not taken).

## Check

Build from NVMe, never from the HDD.

- `DAEDALUS_GPU_REQUIRED=1 DAEDALUS_DMA_HEAP_REQUIRED=1 cargo test -p daedalus-wgpu --test image
  --test import --test region -- --nocapture`, and `cargo test -p daedalus-wgpu-author --test
  pixel`. Record any refusal with its message.
- The cost of an import that is found in the cache (`import_storage` on a buffer already
  imported). `dev` measured 16 to 29 µs per image. Record it, and `storage_import_stats`.
- The direct copy (`ImageCopy`, plan `Direct`) at 640x480 XRGB and at 1280x720. `dev` measured
  0.49 ms and 0.71 ms with the TFU, against 2.9 ms and 8.6 ms for a shader copy. A time near the
  shader's means the TFU wasn't taken: record which.
- GREY at 640x480: the folded copy with a 640-byte stride (plan `Folded { rows: 2 }`, `dev`
  0.43 ms) and the direct copy with a 768-byte stride (`dev` 0.27 ms). Then a stride nothing
  folds, row by row (`dev` 21 ms).
- A buffer allocated with no slack past its last plane is refused with the size it needs.
- A pixel chain of four fed an imported camera texture: one render pass, and its time against
  the same chain fed a buffer (the compute form). `dev` found compute much the slower on V3D.

## Result


Run on 2026-11-10 on the CM5 (raze2): OS image 2026.2.0-dev.993+e1097ec7, kernel 7.2.9-v8-16k, aarch64, 4 cores, 4 GB RAM. V3D 7.1.10.2 through the Broadcom ICD (Vulkan 1.3.354, driver 26.1.8), `/dev/dri/renderD128`. Tested commit: `next` at bdbfe947.

Method: the test binaries were built with `cargo test --release --no-run --target aarch64-unknown-linux-gnu -p <crate>` on NVMe, copied to `/tmp/daedalus-next/bin` on the board, and run as `DAEDALUS_GPU_REQUIRED=1 flock /run/lock/raze-gpu.lock ./<binary> --nocapture --test-threads=1`, with `DAEDALUS_DMA_HEAP_REQUIRED=1` where the variable is named below. Logs are on the board under `/tmp/daedalus-next/logs`.

- `wgpu-image` (with `DAEDALUS_DMA_HEAP_REQUIRED=1`): 2 of 3 pass: `a_folded_copy_that_would_read_past_the_buffer_goes_row_by_row`, `storage_frames_copy_into_textures`. FAIL: `frames_import_once_per_dmabuf_and_read_in_place`, `ERROR_INVALID_EXTERNAL_HANDLE` at `image.rs:163:23` (see E14).
- `wgpu-import`: see E14. `wgpu-region`: 8 of 9 pass, one failure (see E5). `author-pixel`: 7 of 9 pass, two failures (see E6).
- Not run: the cost of an import found in the cache (dev 16 to 29 us per image) and `storage_import_stats`; the direct copy (`ImageCopy`, plan `Direct`) at 640x480 and 1280x720 XRGB (dev 0.49 and 0.71 ms with the TFU, against 2.9 and 8.6 ms for a shader copy); GREY at 640x480 with a 640-byte stride (dev 0.43 ms) and 768-byte stride (dev 0.27 ms), and the row-by-row case (dev 21 ms); and the four-node pixel chain as one render pass against the compute form (dev 2.83 ms against 36.4 ms). This branch has no harness for these timings; writing one is new code, so it was not written.

## Rerun after fixes, 2026-11-10

Same board (CM5, raze2, V3D through the Broadcom ICD), release build, every test binary of the GPU crates, one thread: all pass.

- **The uniform and pixel-chain failures above were not V3D's.** `a_uniform_takes_plain_bytes_or_bytes_already_on_the_device`, `a_config_is_a_port_or_zeroes` and `a_chain_given_a_texture_draws_one` failed in any release build, on the desktop too. The tests built an input cell with `put_inline` from bytes that were gone by the time the step ran, and a debug build happened to still read them. The tests now keep the bytes for the run. The library was right.
- **The dma-heap and dma-buf storage failures above were real, and are fixed.** V3D needs more memory behind an imported buffer than the buffer has bytes, and refused a dma-buf of exactly the buffer's size with `ERROR_INVALID_EXTERNAL_HANDLE`. A dma-heap buffer is now allocated at the size the device asks for, an imported one is given a buffer that fits its dma-buf, and a dma-buf that is too short is refused with both sizes before the driver sees it. `a_dma_heap_buffer_is_one_memory_for_the_host_and_the_device` and `frames_import_once_per_dmabuf_and_read_in_place` pass on V3D.
- Still true: a linear dma-buf image isn't sampled by V3D, so no image has been imported with no copy on this board. That needs frames from the camera pipeline.
- Still true: 8 ops took 2.89 ms in one submit here, against 1.32 ms on `dev`. Not diagnosed.
