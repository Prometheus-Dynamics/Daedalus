## Rerun after fixes, 2026-11-10

Same board (CM5, raze2, V3D through the Broadcom ICD), release build, every test binary of the GPU crates, one thread: all pass.

- **The uniform and pixel-chain failures above were not V3D's.** `a_uniform_takes_plain_bytes_or_bytes_already_on_the_device`, `a_config_is_a_port_or_zeroes` and `a_chain_given_a_texture_draws_one` failed in any release build, on the desktop too. The tests built an input cell with `put_inline` from bytes that were gone by the time the step ran, and a debug build happened to still read them. The tests now keep the bytes for the run. The library was right.
- **The dma-heap and dma-buf storage failures above were real, and are fixed.** V3D needs more memory behind an imported buffer than the buffer has bytes, and refused a dma-buf of exactly the buffer's size with `ERROR_INVALID_EXTERNAL_HANDLE`. A dma-heap buffer is now allocated at the size the device asks for, an imported one is given a buffer that fits its dma-buf, and a dma-buf that is too short is refused with both sizes before the driver sees it. `a_dma_heap_buffer_is_one_memory_for_the_host_and_the_device` and `frames_import_once_per_dmabuf_and_read_in_place` pass on V3D.
- Still true: a linear dma-buf image isn't sampled by V3D, so no image has been imported with no copy on this board.
- Still true: 8 ops took 2.89 ms in one submit here, against 1.32 ms on `dev`. Not diagnosed.

## Next batch, prepared 2026-11-20

The 2026-11-16 `export_fence` figure (0.0017 ms) was on an idle buffer, so it says nothing about a fence
V3D still has to signal. The new section `daedalus-gpu-budgets dma-fence` (`scripts/board/figures/e9.sh`)
asks that:

- A 1 MiB dma-heap buffer is imported into the device.
- The GPU writes it with work sized to still be running at export. The size is calibrated, not set.
- The fence is exported right after the submit. It records whether it is a sync_file
  (`SYNC_IOC_FILE_INFO`), whether it was unsignalled at export, the time to signal (median of 50 after
  5), and whether a CPU read of the dma-buf afterwards sees the GPU's values.
- Where the import is refused, or the fence was signalled at export, it prints `skipped:` with the reason.

The command, ranges and rules are in `run-sheet.md`.

## Result, 2026-11-20

Run on 2026-11-20 on the CM5 (raze2, serial a317bcbee5226d57) in the batched session, at `next` 0d5760f8: OS image 2026.2.0-dev.993+e1097ec7, kernel 7.2.9-v8-16k, V3D 7.1.10.2. The commands, ranges and rules are in `run-sheet.md`; `scripts/board/judge.py figures` judged the results.

Judge: FAIL (skipped on the board).

- The device imported the 1 MiB dma-heap buffer in place.
- The sync_file exported from the dma-buf right after the submit was already signalled, after a GPU
  write of 87.3 ms (128 loop rounds).

Finding: v3dv does not put its job on an imported dma-buf's implicit fence, so a fence exported from
the dma-buf can't carry V3D's write. A reader that waits on it can read before the write ends. The
writer's own fence has to be handed over: the submit's sync fd, either attached to the dma-buf
(`DMA_BUF_IOCTL_IMPORT_SYNC_FILE`) or passed to the reader. E9 is measured again on that, in the next
board session.
