Status: partly run on CM5 2026-11-10 (two pixel tests fail on V3D; timings not taken).

## Check

Build from NVMe, never from the HDD.

- `DAEDALUS_GPU_REQUIRED=1 cargo test -p daedalus-wgpu-author --test pixel`: all nine have to
  pass.
- Eight pixel nodes on 1280x800, as one merged fragment pass (`merge::fragment_pass`): time it as
  the median of 200 after 20 warm-up runs. It must be one submit and one pass, and cost no more
  than the single box 3x3 fragment pass (`dev` 2.83 ms) plus the arithmetic of the extra nodes.
- The same eight nodes as the merged compute form through a region, and as eight unmerged
  regions. Record all three numbers: `dev` measured storage-buffer compute at 36.4 ms against
  2.83 ms for the fragment pass on a box 3x3, which is why V3D is meant to get the fragment form.

## Rerun after fixes, 2026-11-10

Same board (CM5, raze2, V3D through the Broadcom ICD), release build, every test binary of the GPU crates, one thread: all pass.

- **The uniform and pixel-chain failures above were not V3D's.** `a_uniform_takes_plain_bytes_or_bytes_already_on_the_device`, `a_config_is_a_port_or_zeroes` and `a_chain_given_a_texture_draws_one` failed in any release build, on the desktop too. The tests built an input cell with `put_inline` from bytes that were gone by the time the step ran, and a debug build happened to still read them. The tests now keep the bytes for the run. The library was right.
- **The dma-heap and dma-buf storage failures above were real, and are fixed.** V3D needs more memory behind an imported buffer than the buffer has bytes, and refused a dma-buf of exactly the buffer's size with `ERROR_INVALID_EXTERNAL_HANDLE`. A dma-heap buffer is now allocated at the size the device asks for, an imported one is given a buffer that fits its dma-buf, and a dma-buf that is too short is refused with both sizes before the driver sees it. `a_dma_heap_buffer_is_one_memory_for_the_host_and_the_device` and `frames_import_once_per_dmabuf_and_read_in_place` pass on V3D.
- Still true: a linear dma-buf image isn't sampled by V3D, so no image has been imported with no copy on this board.
- Still true: 8 ops took 2.89 ms in one submit here, against 1.32 ms on `dev`. Not diagnosed.

## Timings, 2026-11-10

Built with `cargo build --release --target aarch64-unknown-linux-gnu -p daedalus-gpu-budgets` and run as `flock /run/lock/raze-gpu.lock ./daedalus-gpu-budgets <section>` on the CM5 (raze2): OS image 2026.2.0-dev.993+e1097ec7, kernel 7.2.9-v8-16k, V3D 7.1.10.2. Tested commit: `next` at a2ed64ea plus the timing sections of this PR. Each figure is a median of 50 runs after 5 warm-up runs, unless a line says otherwise. Three runs were made of each section, and the ranges below are the lowest and highest medians across them.

Pixel chains, from the `chains` section: four pixel bodies (HALF_TO_F32, F32_TO_UNORM8 twice) over 1 M values, as one merged shader, and as four separate shaders run one after the other with each waited for before the next (a shader answers `Busy` while another run of it is in flight, so the separate nodes cannot overlap). The command is `daedalus-gpu-budgets chains`, three runs.

- One merged shader: 9.957 to 10.032 ms.
- Four separate shaders: 29.670 to 29.862 ms.

Merged is about three times faster than the separate nodes at this size. This is not E6's workload: E6 asks for eight nodes on 1280x800 as the fragment pass, the merged compute form and eight unmerged regions, against dev's 2.83 ms fragment and 36.4 ms compute. Not run: the 1280x800 timings, the fragment form (`merge::fragment_pass`), and the eight-node chain. The two `author-pixel` failures recorded above are unchanged by this PR.

## Timings, 2026-11-11

Build: this branch, based on `origin/next` at 9039013d. Three CM5 runs (OS image 2026.2.0-dev.993+e1097ec7, V3D 7.1.10.2), `daedalus-gpu-budgets pixels busy cached heap-read` under `flock /run/lock/raze-gpu.lock`. Each figure is a median of 50 after 5 warm-up runs, and the ranges are the lowest and highest of the three runs.

The pixel chains on a 1280x800 frame, each pixel an authored `vec4<u32>` body (`gaps.inc4`, `gaps.twice4`), 8 nodes for the procedure's workload and 4 for E15's. Command: `daedalus-gpu-budgets pixels`.

| case | run 1 | run 2 | run 3 | reference |
|---|---|---|---|---|
| 8 nodes, fragment pass (one submit, one pass) | 1.836 ms | 1.769 ms | 1.959 ms (see below) | dev 2.83 ms for the box 3x3 fragment pass; the merged fragment pass must not cost more |
| 8 nodes, merged compute pass through one region | 7.991 ms | 8.041 ms | 7.987 ms | dev 36.4 ms (storage-buffer compute) |
| 8 nodes, one compute region per node | 59.765 ms | 59.624 ms | 59.654 ms | no dev figure |

The fragment pass for 8 nodes is 1.77 to 1.96 ms over the three runs, under dev's 2.83 ms, so it meets the reference. The merged compute pass is about a fifth of dev's 36.4 ms, so the compute form here meets it. The unmerged form is 7.5 times the merged compute form.

Both the fragment and the compute measurements end with the device's work done: the fragment with its ticket's wait, the compute with a four-byte read of its output.
