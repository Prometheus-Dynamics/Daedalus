# Board run: E14 dma-buf import on V3D

Status: partly run on CM5 2026-11-10 (linear imports refused as the procedure expects; the zero-copy import never ran on V3D; timings not taken).

## Check

Build from NVMe, never from the HDD.

- `DAEDALUS_GPU_REQUIRED=1 cargo test -p daedalus-wgpu --test import -- --nocapture`. V3D doesn't
  sample a linear image, so the linear imports of that test have to be refused there with that
  reason: record the message.
- With frames from the camera pipeline (tiled, Broadcom UIF or SAND), written as a small test
  beside `import.rs`: an XRGB frame imports with no copy, an NV12 frame imports as one texture
  with one memory plane, and a frame shorter than the layout plus 256 bytes is refused with the
  size it needs.
- A frame whose producer is still writing: the import with its fence waits on the device, with
  no host wait. `dev` measured 0.2 ms for that wait on an exported frame. Record it.
- Steady state: import the same eight buffers in rotation for 1000 frames. Record the
  allocations per import (`dev` measured 44 to 50) and that `import_stats` shows 8 imports and
  the rest hits.

## Result


Run on 2026-11-10 on the CM5 (raze2): OS image 2026.2.0-dev.993+e1097ec7, kernel 7.2.9-v8-16k, aarch64, 4 cores, 4 GB RAM. V3D 7.1.10.2 through the Broadcom ICD (Vulkan 1.3.354, driver 26.1.8), `/dev/dri/renderD128`. Tested commit: `next` at bdbfe947.

Method: the test binaries were built with `cargo test --release --no-run --target aarch64-unknown-linux-gnu -p <crate>` on NVMe, copied to `/tmp/daedalus-next/bin` on the board, and run as `DAEDALUS_GPU_REQUIRED=1 flock /run/lock/raze-gpu.lock ./<binary> --nocapture --test-threads=1`, with `DAEDALUS_DMA_HEAP_REQUIRED=1` where the variable is named below. Logs are on the board under `/tmp/daedalus-next/logs`.

- `wgpu-import` without `DAEDALUS_DMA_HEAP_REQUIRED`: 4 of 4 pass. Each linear import returns the typed refusal, so none of them imports. These passes are the refusal path only.
- `wgpu-import` with `DAEDALUS_DMA_HEAP_REQUIRED=1`: 0 of 4 pass. Each one panics at the refusal the procedure expects, and the helper `unsupported` turns that refusal into a failure when the variable is set:
  - `a_type_that_describes_itself_is_imported_by_its_transfer` at `backends/wgpu/tests/import.rs:337:13`: `R8 with modifier 0x0: V3D doesn't sample a linear image: copy it into a texture instead`.
  - `dmabuf_import_is_zero_copy` at `import.rs:54:5`: `AB24 with modifier 0x0: V3D doesn't sample a linear image: copy it into a texture instead`.
  - `dmabuf_import_nv12_as_one_texture` at `import.rs:54:5`: `NV12 with modifier 0x0: V3D doesn't sample a linear image: copy it into a texture instead`.
  - `dmabuf_import_rejects_non_dmabuf_and_short_buffers` at `import.rs:54:5`: `AB24 with modifier 0x0: V3D doesn't sample a linear image: copy it into a texture instead`.
  The refusal is correct and the message is the one the procedure expects. The test fails under this variable by its own design, and no zero-copy or NV12 import ran on V3D.
- `wgpu-image`, `frames_import_once_per_dmabuf_and_read_in_place`: FAIL at `backends/wgpu/tests/image.rs:163:23`, message `the import: Vulkan: ERROR_INVALID_EXTERNAL_HANDLE`. That is a raw Vulkan error, not the typed refusal the test allows for, so it is a finding. Not diagnosed. It fails with or without `DAEDALUS_DMA_HEAP_REQUIRED`.
- Not run: the camera-frame checks (an XRGB frame with no copy, an NV12 frame as one texture, a short frame refused with its size). They need a test written beside `import.rs` for real camera frames, which does not exist, and the procedure says not to invent it. Not run: the 1000-frame steady state with eight buffers in rotation (the allocations per import and `import_stats`), and the fence-wait timing (dev 0.2 ms).

## Rerun after fixes, 2026-11-10

Same board (CM5, raze2, V3D through the Broadcom ICD), release build, every test binary of the GPU crates, one thread: all pass.

- **The uniform and pixel-chain failures above were not V3D's.** `a_uniform_takes_plain_bytes_or_bytes_already_on_the_device`, `a_config_is_a_port_or_zeroes` and `a_chain_given_a_texture_draws_one` failed in any release build, on the desktop too. The tests built an input cell with `put_inline` from bytes that were gone by the time the step ran, and a debug build happened to still read them. The tests now keep the bytes for the run. The library was right.
- **The dma-heap and dma-buf storage failures above were real, and are fixed.** V3D needs more memory behind an imported buffer than the buffer has bytes, and refused a dma-buf of exactly the buffer's size with `ERROR_INVALID_EXTERNAL_HANDLE`. A dma-heap buffer is now allocated at the size the device asks for, an imported one is given a buffer that fits its dma-buf, and a dma-buf that is too short is refused with both sizes before the driver sees it. `a_dma_heap_buffer_is_one_memory_for_the_host_and_the_device` and `frames_import_once_per_dmabuf_and_read_in_place` pass on V3D.
- Still true: a linear dma-buf image isn't sampled by V3D, so no image has been imported with no copy on this board. That needs frames from the camera pipeline.
- Still true: 8 ops took 2.89 ms in one submit here, against 1.32 ms on `dev`. Not diagnosed.

## Timings, 2026-11-10

Built with `cargo build --release --target aarch64-unknown-linux-gnu -p daedalus-gpu-budgets` and run as `flock /run/lock/raze-gpu.lock ./daedalus-gpu-budgets <section>` on the CM5 (raze2): OS image 2026.2.0-dev.993+e1097ec7, kernel 7.2.9-v8-16k, V3D 7.1.10.2. Tested commit: `next` at a2ed64ea plus the timing sections of this PR. Each figure is a median of 50 runs after 5 warm-up runs, unless a line says otherwise. Three runs were made of each section, and the ranges below are the lowest and highest medians across them.

Camera frames and dma-buf imports. The command is `DAEDALUS_CAMERA_REQUIRED=1 DAEDALUS_GPU_REQUIRED=1 DAEDALUS_DMA_HEAP_REQUIRED=1 flock /run/lock/raze-gpu.lock ./camera_frames-<hash> --nocapture --test-threads=1`, the test in `testing/crates/camera-fixture/tests/camera_frames.rs`. The camera is `/dev/video0` ("Creative Live! Cam Sync V3"). The first capture node that streams was used; `/dev/video1` onward were not opened once a free one was found. The camera streams YUYV 640x480, bytesperline 1280, sizeimage 614400, with four MMAP buffers exported with `VIDIOC_EXPBUF`. The frame is imported as an R8 storage image 1280 bytes a row. Two runs.

Results:

- A whole frame is refused: `the dma-buf is 614400 bytes, and this device needs 614656 for the image`. The camera's buffer is exactly its frame, and V3D needs 256 bytes past the last plane. The test then imports the frame one row short (479 rows, 613120 bytes). Nothing else was changed. A camera frame cannot be imported whole on V3D with this rule. Whether the rule should be relaxed for an import that never reads past its last row is a decision for the GPU session.
- `import_external` of the linear frame is refused: `V3D doesn't sample a linear image: copy it into a texture instead`. That is the refusal the procedure expects.
- Zero copy: the import reuses the dma-buf's identity (`storage_import_stats`: 4 imports, 396 hits, 0 evictions over 400 frames). The import of a buffer the first time is 0.094 to 0.148 ms (median); a cache hit is 9.6 to 10.5 us (median). Dev measured 16 to 29 us for a cache hit, so the hit is faster than dev's figure.
- Copy shader over the imported frame (`Kernel::Copy`, 613120 bytes): median 1.30 to 1.61 ms.

Correctness, which does not pass: the device reads the frame's bytes correctly on first use of each buffer (4 of 4 first uses match the host), and wrong on every reuse (0 of 396 match). The host's view of the same memory is stable across the device run (it reads the same bytes before and after), so the camera's frame is in memory and the host sees it. The image copy into a texture also differs on 387 to 393 frames. The test fails on this.

What I tried, and what it ruled out:
- A `begin_cpu_access` and `end_cpu_access` (read and write) of the dma-buf before each device read. It did not change the result.
- The same import and sync on a dma-heap buffer that the host rewrites: the device reads each new fill through the cached import (3 of 3 rewrites). So the cached import itself works on V3D for memory the host writes with a sync around the write.

What remains different for the camera is that its frames are written by the camera driver into V4L2 MMAP memory, and that path's dma-buf sync evidently does not make the CPU's writes visible to the device on reuse. I have not found the mechanism, and I have not confirmed the kernel's exporter behaviour. A fix belongs in the fixture or the driver path, and is not made here.

Not run: the fence-wait timing of a frame whose producer is still writing (dev 0.2 ms), and the steady-state allocations per import of eight buffers in rotation (dev 44 to 50). The 1000-frame loop was run as 400 frames.
