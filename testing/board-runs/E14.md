  - `a_type_that_describes_itself_is_imported_by_its_transfer` at `backends/wgpu/tests/import.rs:337:13`: `R8 with modifier 0x0: V3D doesn't sample a linear image: copy it into a texture instead`.

## Rerun after fixes, 2026-11-10

Same board (CM5, raze2, V3D through the Broadcom ICD), release build, every test binary of the GPU crates, one thread: all pass.

- **The uniform and pixel-chain failures above were not V3D's.** `a_uniform_takes_plain_bytes_or_bytes_already_on_the_device`, `a_config_is_a_port_or_zeroes` and `a_chain_given_a_texture_draws_one` failed in any release build, on the desktop too. The tests built an input cell with `put_inline` from bytes that were gone by the time the step ran, and a debug build happened to still read them. The tests now keep the bytes for the run. The library was right.
- **The dma-heap and dma-buf storage failures above were real, and are fixed.** V3D needs more memory behind an imported buffer than the buffer has bytes, and refused a dma-buf of exactly the buffer's size with `ERROR_INVALID_EXTERNAL_HANDLE`. A dma-heap buffer is now allocated at the size the device asks for, an imported one is given a buffer that fits its dma-buf, and a dma-buf that is too short is refused with both sizes before the driver sees it. `a_dma_heap_buffer_is_one_memory_for_the_host_and_the_device` and `frames_import_once_per_dmabuf_and_read_in_place` pass on V3D.
- Still true: a linear dma-buf image isn't sampled by V3D, so no image has been imported with no copy on this board.
- Still true: 8 ops took 2.89 ms in one submit here, against 1.32 ms on `dev`. Not diagnosed.

  0.215 ms after the signal (the reference's wait is 0.2 ms).
- Planted copy with no wait: the sentinel in 0 of 50. Finding: once the fence is attached to the
  dma-buf, V3D's kernel makes the second device's job wait for it even though the job doesn't wait
  itself. That is the attach working, but it leaves the plant unable to catch a consumer that
  doesn't wait. Fixed: the planted copy now follows a write by a device with attaching off.

## Result, 2026-11-21, third session

Raze #2 (serial a317bcbee5226d57), image 993, `next` a6fc6358, the layer at the pinned v1.4.354
(aarch64 sha256 4833dd1b…). Only E13, E9 and E14 ran (`BATCH_FIGURES="e9 e14"`). Results in the
session's copy, `raze2-batch-2026-11-21`.

- Steady imports: 8 device imports, 992 cache hits, 0 copies. Allocations per import 12 to 16 for
  the first eight, then a median of 3.
- Device-side wait: the producer was still writing at the consumer's submit in 50 of 50, and the
  copy saw the GPU's values in 50 of 50. Host submit 0.054 ms. The copy finished 0.243 ms after the
  signal (the reference's wait is 0.2 ms).
- Planted copy with no wait: the sentinel in 0 of 50. This time the write came from a device with
  attaching off, and E9 (c) shows that such a write leaves no fence on the buffer. So the second
  session's reading, that the kernel waited on the attached fence, was wrong. The order comes
  from V3D itself: on one V3D, a job that a second device submits after the write runs after it.
  The plant can't catch a consumer that doesn't wait on a board with one V3D. It needs two GPUs, or
  a producer the host holds back past the consumer's submit.

E14: FAIL on the plant only, for the reason above.
