# Board run: E17 dma-buf blocks on the CM5

The `daedalus-dmabuf` memory backend this run was first written for has been removed: nothing planned through it. The `daedalus-dmabuf` test results below are kept as the record of that run. The dma-heap figures further down are for the GPU backend's own buffers, which stay.

Status: subject gone. The dma-buf checks in this record ran on CM5 2026-11-10 (17 of 17 pass, with no skips). The `daedalus-dmabuf` crate they test was removed in #194 (commit `2c3e259c`), so those checks can no longer be run and their Check lines below are kept only as history. Timings not taken. The dma-heap read timing that remains is `daedalus-gpu-budgets heap-read`, which is in the Check below.

## Check

Build from NVMe, never from the HDD.

- Not runnable on `next`: `cargo test -p daedalus-dmabuf` and `Source::Heap("system")` belong to the removed crate.
- Time, as the median of 50, reading back a 1 MiB and a 16 MiB dma-heap buffer made by the GPU backend
  (`Storage::new_dma_heap`): `DAEDALUS_GPU_REQUIRED=1 DAEDALUS_DMA_HEAP_REQUIRED=1 ./daedalus-gpu-budgets heap-read`,
  built with `cargo build --release --target aarch64-unknown-linux-gnu -p daedalus-gpu-budgets`.
  `dev` measured 3.6 ms for 16 MiB from a dma-heap buffer and 13.1 ms from V3D's own host-visible memory.

## Follow-up, the 16 MiB dma-heap read gap, 2026-11-11

Build: this branch, based on `origin/next` at 3b0bdccb. Tool sections `heap-probe` (one process, all variants in order) and `heap-alone` (one variant per process, with `ALONE=`), CM5 under `flock /run/lock/raze-gpu.lock`. Reference: dev's 3.6 ms for the 16 MiB read.

Measured, in the order the probes take the variants (`heap-probe`, three runs):

| read | run 1 | run 2 | run 3 |
|---|---|---|---|
| storage `read_into`, reused Vec | 4.368 ms | 4.268 ms | 4.195 ms |
| raw sync, copy, sync, reused Vec | 3.338 ms | 3.306 ms | 3.327 ms |
| raw copy, no sync, reused Vec | 3.342 ms | 3.325 ms | 3.315 ms |
| raw sync per 64 KiB chunk, reused Vec | 4.197 ms | 4.199 ms | 4.235 ms |
| storage `read_into`, fresh zeroed Vec | 7.503 ms | 7.303 ms | 6.827 ms |
| raw sync, copy, sync, fresh zeroed Vec | 6.668 ms | 6.727 ms | 6.684 ms |

The fresh-Vec rows are the page faults of first touch: a new 16 MiB Vec costs about 3.3 ms more than a reused one, on both paths. The tool now reuses its destination for the timed read, so the measured figures are not those rows.

Each variant alone in its own process (`heap-alone`, 9 storage runs and 9 raw runs, alternating): storage read 4.07 to 4.93 ms; raw sync, copy, sync 3.29 to 4.10 ms, median near 3.5 ms. So the gap is not an effect of the order the probes run in.

The cause, found by importing a raw dma-buf of the storage's length into the device and then reading its mapping from the host (`heap-alone imported`, three runs): the raw read after the device import is 4.23 to 4.72 ms, and the same read without an import is 3.48 to 3.87 ms. The import is what slows the host's read of the memory. The read routine is the same in both: the library's `Mapping::read` is the same begin, copy, end sequence as the raw measurement, and a single sync per read costs nothing measurable (0.001 ms for the pair). A sync per 64 KiB chunk does cost (about 0.9 ms over the 256 chunks), which is why the library's one sync per read is the right shape and the per-chunk variant is not used.

So the 0.7 ms is the device-visible memory itself, on this board's V3D driver: a dma-heap buffer the device imports is read by the host about 20 percent slower than one it does not. The 3.6 ms of dev's figure is for a buffer the device does not import, and the raw read meets it (3.3 to 3.9 ms). The storage read, which must be device-visible for the readback to write it, is 4.1 to 4.9 ms against that reference.

No library change follows from this: the read path is correct and the cost is at the device import. I did not find a way to keep a readback target device-visible and read it at the unimported speed. The readback route still beats the host-mapped route (E3: 12.1 to 12.3 ms against 16.8 to 17.7 ms for the same 16 MiB readback).

## Reference rerun, the 16 MiB dma-heap read (reference-rerun, 2026-11-11)

The reference's 3.6 ms is the `copy` column of its `readback` section
(`crates/gpu/examples/gpu_bench/linux/frame_import.rs`, `readback`). The section maps a system dma-heap
buffer, imports it as a storage buffer, runs a kernel that writes it, syncs the CPU access, then times
`copy_from_slice` of the mapping into a reused host Vec. The sync is timed separately. The imported
buffer is alive during the copy, so the copy runs against device-imported memory.

Ours: `Storage::new_dma_heap`, then `read_into` (the storage's own mapping, a plain `copy_nonoverlapping`,
no sync). `heap-read` also times a raw read of a plain dma-heap buffer, with the sync, with and without
the device buffer alive.

| Row | reference, run 1 / 2 / 3 | reference median | ours, run 1 / 2 / 3 | ours median |
|---|---|---|---|---|
| copy, device buffer alive, ms | 3.404 / 3.589 / 3.822 | 3.589 | `read_into` 4.383 / 4.785 / 4.276 | 4.383 |
| sync, ms | 0.313 / 0.335 / 0.397 | 0.335 | none (`read_into` has no sync) | |
| copy + sync, device buffer alive, ms | 3.717 / 3.924 / 4.219 | 3.924 | raw read 4.142 / 4.036 / 3.292 | 4.036 |
| copy + sync, device buffer dropped, ms | | | raw read 3.314 / 3.329 / 3.664 | 3.329 |

Result: like for like, copy plus sync against the device buffer alive, ours (4.04 ms) and the reference
(3.92 ms) are at parity within the run-to-run spread. The one path that is slower is our storage
`read_into`, at 4.38 ms against the reference's 3.59 ms copy alone, which is 0.8 ms more. Our raw read
of a plain dma-heap buffer is faster than the reference's copy with the device buffer dropped, and the
device buffer being alive costs about 0.7 ms on our raw read too. What makes `read_into` slower than our
own raw read, 0.35 ms, has not been isolated; that is the open item for this path. Not ported here.

## The read_into gap, isolated (read-into-gap, 2026-11-11)

The gap was `Storage::read_into` on a 16 MiB dma-heap buffer against our raw read of the same kind
of mapping. Measured on the CM5 today, `flock /run/lock/raze-gpu.lock ./daedalus-gpu-budgets
heap-read`, three runs each, and the reference's `readback` from `daedalus-gpu` `gpu_bench` on
dev at `96747965`, three runs each, for the same copy.

What the library's read does, read from the code: `Storage::read_into` checks the range (a multiple of
4 bytes and not empty), then `Mapping::read`, which calls `begin_cpu_access(Read)`, one `copy_nonoverlapping`
of the whole range, then `end_cpu_access(Read)`. A raw dma-heap mapping in the tool does the same
three steps. There is no lock in the mapping. The copy is one piece. The destination is the same
vector in both, touched by the warm-up runs before the timed reads.

The decomposition, in the state the reference measures (a GPU kernel writes the imported buffer, then
the CPU sync and read run):

| Row | ours, run 1 / 2 / 3 | ours median | reference, run 1 / 2 / 3 | reference median |
|---|---|---|---|---|
| sync (begin and end CPU access), ms | 0.610 / 0.544 / 0.585 | 0.585 | 0.313 / 0.335 / 0.397 | 0.335 |
| full read, sync and copy, ms | 4.201 / 4.030 / 3.878 | 4.030 | copy and sync 3.717 / 3.924 / 4.219 | 3.924 |
| copy alone, ms (full read minus sync, ours; `copy` column, reference) | 3.591 / 3.486 / 3.293 | 3.486 | 3.404 / 3.589 / 3.822 | 3.589 |
| raw dma-heap read, sync and copy, device buffer dropped, ms | 3.912 / 3.300 / 3.336 | 3.336 | | |

The raw sync on a plain dma-heap buffer is 0.001 ms, because nothing is imported into the device. The
0.59 ms is the imported buffer's cache maintenance, and the reference pays a smaller one (0.34 ms) on
its own imported buffer.

Before (the state the first comparison was made in, a host write then the read): `read_into` 4.894 /
4.459 / 4.999 ms against the raw read's 3.521 / 3.362 / 3.594 ms with the device buffer alive. That is
the 0.35 ms gap as first reported. In that state the storage's sync is 0.466 ms.

After: no library change. In the matched state the copy alone is 3.49 ms on ours and 3.59 ms on the
reference, so the copy is not slower. The full read with its sync is 4.03 ms on ours against the
reference's 3.92 ms, at parity within the run-to-run spread. The remaining difference is the sync,
0.59 ms against 0.34 ms.

What would close the sync: the sync is whole-buffer cache maintenance on an imported dma-buf, and
skipping it when the device has not written the buffer since the last sync would save about 0.5 ms a
read. That changes the storage's correctness contract (the backend must track device writes to the
buffer), so it is not made here. Open, with that lever named.

Not checked: whether the reference's sync figure is on the same memory size as ours (both are 16 MiB,
padded the same way by `need`), and whether the padding itself adds to the sync (not isolated).

## heap-read-sync: the sync is skipped when the device can't have written (2026-11-11)

Backend change: the dma-heap mapping keeps a "the device may have written since the host last synced"
flag. Every device use of the buffer goes through `Storage::buffer()` (and `wgpu()`, which calls it), and
sets the flag with an atomic store. A read clears it and does its sync; a read with the flag clear does
no sync. Writes keep their own begin and end, as before. A new or imported buffer starts with the flag set.
The bind-group path calls `buffer()` for each storage on every dispatch, before the cache lookup, so a
cached bind group does not hide a device use.

CM5, `flock /run/lock/raze-gpu.lock ./daedalus-gpu-budgets heap-read`, three runs each. The reference
row is dev's `readback` copy-plus-sync after a GPU write, from the record above: 3.92 ms.

| Row | before, median (runs) | after, median (runs) |
|---|---|---|
| `read_into`, after a host write, ms | 4.894 (4.894 / 4.459 / 4.999) | 3.711 (3.370 / 3.711 / 3.925) |
| `read_into` repeated, no device use between, ms | 4.19 to 4.84 | 3.798 (3.289 / 3.934 / 3.798) |
| sync of a four-byte read, no device use, ms | 0.466 | 0.000 (the sync is skipped) |
| full read after a GPU write, ms | 4.030 (4.201 / 4.030 / 3.878) | 4.133 (3.779 / 4.133 / 4.331) |
| sync after a GPU write, ms | 0.585 (0.610 / 0.544 / 0.585) | 0.561 (0.579 / 0.526 / 0.561) |
| raw dma-heap read, sync and copy, device dropped, ms | 3.336 | 3.367 (3.782 / 3.367 / 3.278) |
| reference, copy plus sync after a GPU write, ms | 3.924 | 3.924 |

Read: a read with no device use in between is now as fast as a plain copy (the sync is gone). The
row that matches the reference's condition, a read right after a device write, still needs its sync,
and is unchanged within the spread: 4.13 ms on ours (median of three; 3.78 to 4.33) against the
reference's 3.92 ms. The sync after a GPU write (0.56 ms) is the remaining difference, and the
skip cannot remove it, because the device wrote the buffer.

Tests (backends/wgpu/tests/storage.rs), all passing on the CM5 three times with
`DAEDALUS_DMA_HEAP_REQUIRED=1`: `a_read_after_a_device_write_sees_the_devices_bytes` (the device writes
the heap, the work's fence is waited on, then the host reads the device's bytes), and
`a_read_with_no_device_use_in_between_does_no_sync` (a counter of syncs: the first read syncs, two
reads with no device use in between do not, a device write makes the next read sync once).
