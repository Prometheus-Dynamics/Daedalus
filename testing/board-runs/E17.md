# Board run: E17 dma-buf blocks on the CM5

Status: partly run on CM5 2026-11-10 (dma-buf tests pass with no skips; timings not taken).

## Check

Build from NVMe, never from the HDD.

- `cargo test -p daedalus-dmabuf -- --nocapture`: nothing may print `skipped`.
- With `Source::Heap("system")`: take and drop a 1 MiB block 1000 times after a warm-up, and
  record that the counting allocator sees no allocation and the pool's `allocated` stays at 1.
- Time, as the median of 50, reading back a 1 MiB and a 16 MiB heap block through
  `block.access(Access::Read)`. `dev` measured 3.6 ms for 16 MiB from a dma-heap buffer and
  13.1 ms from V3D's own host-visible memory.

## Result


Run on 2026-11-10 on the CM5 (raze2): OS image 2026.2.0-dev.993+e1097ec7, kernel 7.2.9-v8-16k, aarch64, 4 cores, 4 GB RAM. V3D 7.1.10.2 through the Broadcom ICD (Vulkan 1.3.354, driver 26.1.8), `/dev/dri/renderD128`. Tested commit: `next` at bdbfe947.

Method: the test binaries were built with `cargo test --release --no-run --target aarch64-unknown-linux-gnu -p <crate>` on NVMe, copied to `/tmp/daedalus-next/bin` on the board, and run as `DAEDALUS_GPU_REQUIRED=1 flock /run/lock/raze-gpu.lock ./<binary> --nocapture --test-threads=1`, with `DAEDALUS_DMA_HEAP_REQUIRED=1` where the variable is named below. Logs are on the board under `/tmp/daedalus-next/logs`.

- `dmabuf-memory` (`DAEDALUS_DMA_HEAP_REQUIRED=1`): 17 of 17 pass, including `steady_state_reuse_allocates_nothing`, `steps_do_not_allocate` and `the_pool_reuses_up_to_four_idle_blocks_and_drops_the_fifth`. `cargo test -p daedalus-dmabuf` printed no `skipped`. `dmabuf-lib` has no tests.
- Not run: the 1000 take-and-drop loop of a 1 MiB block from `Source::Heap("system")` under the counting allocator, with the pool's `allocated` checked at 1 (the steady-state test is the nearest, and is not the same loop); and the median of 50 reads of a 1 MiB and a 16 MiB heap block through `block.access(Access::Read)` (dev 3.6 ms for 16 MiB from a dma-heap buffer and 13.1 ms from V3D's host-visible memory). This branch has no harness for them; writing one is new code, so it was not written.

## Timings, 2026-11-10

Built with `cargo build --release --target aarch64-unknown-linux-gnu -p daedalus-gpu-budgets` and run as `flock /run/lock/raze-gpu.lock ./daedalus-gpu-budgets <section>` on the CM5 (raze2): OS image 2026.2.0-dev.993+e1097ec7, kernel 7.2.9-v8-16k, V3D 7.1.10.2. Tested commit: `next` at a2ed64ea plus the timing sections of this PR. Each figure is a median of 50 runs after 5 warm-up runs, unless a line says otherwise. Three runs were made of each section, and the ranges below are the lowest and highest medians across them.

dma-heap buffers, from `Storage::new_dma_heap` (device read and write through `Storage::read_into` and `write`), and the transfers section. The command is `daedalus-gpu-budgets transfers`, run on its own.

| size | dma-heap write | dma-heap read | host-mapped read (device memory, mapped) |
|---|---|---|---|
| 4 KiB | 0.001 ms | 0.003 to 0.004 ms | 0.003 to 0.004 ms |
| 256 KiB | 0.026 to 0.053 ms | 0.051 to 0.073 ms | 0.165 to 0.198 ms |
| 4 MiB | 0.880 to 0.978 ms | 0.953 to 1.169 ms | 2.895 to 3.274 ms |

The dma-heap read of 4 MiB is 0.95 to 1.17 ms. Dev's figure is for 16 MiB (3.6 ms from a dma-heap buffer, 13.1 ms from V3D's host-visible memory), and the 16 MiB size was not reached on the board (see E3). So I cannot say from this run whether the 16 MiB figure meets dev's.

Not run: the 1000-iteration take-and-drop loop of a 1 MiB heap block under the counting allocator, the median of 50 reads of a 1 MiB and a 16 MiB heap block through `block.access(Access::Read)`, and the sync_file export of a dma-buf V3D has just written. The 1 MiB and 16 MiB sizes and the access path are not in the transfers section.

## Follow-up, 16 MiB dma-heap buffer, 2026-11-10

Three CM5 runs of the transfers section, the same build as E3:

| case | run 1 | run 2 | run 3 | dev figure |
|---|---|---|---|---|
| 16 MiB dma-heap write | 3.747 ms | 3.802 ms | 4.234 ms | not quoted |
| 16 MiB dma-heap read (through `read_into`) | 4.317 ms | 4.367 ms | 4.326 ms | 3.6 ms from a dma-heap buffer |

The dma-heap read misses dev's 3.6 ms by about 20 percent. Not run: the median of 50 with `begin_cpu_access` and `end_cpu_access` around the read (the read here goes through the same `read_into` as the other rows, without the explicit sync), and the 1 MiB rows.
