# Board run: C24 tick-path overhead

Status: run on CM5 2026-11-10 (probe off and on, and the window overhead, taken with `cpu-timings`).

## Check

- The tick-path overhead of a 16-stage chain with `TickProbe` off and on, against `dev`'s tick overhead numbers.
- With the probe off the run path adds one `None` check per step, so the overhead with it off must match C1's per-stage figures.
- Record the per-tick `overhead_ns` from `TickOverheadWindow::report` next to the probe-off time per tick.

## Result


Run on 2026-11-10 on the CM5 (raze2): OS image 2026.2.0-dev.993+e1097ec7, kernel 7.2.9-v8-16k, aarch64. Tested commit: `next` at bdbfe947.

- `core/host` probe tests built with `cargo test --release --no-run --target aarch64-unknown-linux-gnu -p daedalus-host` and run on the board as `probe --nocapture --test-threads=1`: 4 of 4 pass. That includes `a_warm_tick_with_a_probe_attached_allocates_nothing`, `take_tick_resets_the_probe_and_peek_does_not`, `the_window_keeps_the_last_ticks_and_derives_the_remainder` and `diagnostics_round_trip_as_json`.
- Not run: the 16-stage chain's tick time with `TickProbe` off and on, and the per-tick `overhead_ns` from `TickOverheadWindow::report`. This branch has no timing harness that drives the probe, and writing one is new code, so it was not written.

## Timings (cpu-timings, 2026-11-10)

Board: CM5 (raze2), kernel 7.2.9-v8-16k, aarch64, 4 cores, CPU governor `performance`. Built on
NVMe with `CARGO_TARGET_AARCH64_UNKNOWN_LINUX_GNU_LINKER` and `CC_aarch64_unknown_linux_gnu` set to
`/mnt/nvme-wd/scratch/zigcc/aarch64-cc`, as `cargo build --release --target aarch64-unknown-linux-gnu -p
daedalus-cpu-timings`. Copied to a directory of mine under `/tmp` on the board, run there, and removed
afterwards. Each section prints the median of 101 batches of 1,000 calls, after 20 warm batches; the
times are per call, in ns.

Commands: `daedalus-cpu-timings probe_off` and `daedalus-cpu-timings probe_on`, three runs each. The
workload is C1's 16-stage unfused chain (`budget_harness::chain(16, Stage::Plain, false)`, one feed
and one take a tick). The probe is attached to the host's runner with `set_probe`. The window
(`TickOverheadWindow`, 1,000 ticks) records every tick, and its figures are for the last batch.

| Row | run 1 | run 2 | run 3 | median of runs |
|---|---|---|---|---|
| Tick, probe off, ns | 1,868.9 | 1,866.6 | 1,866.0 | 1,866.6 |
| Tick, probe off, per stage, ns | 116.8 | 116.7 | 116.6 | 116.7 |
| Tick, probe on, ns (includes recording the window) | 3,478.8 | 3,518.8 | 3,499.7 | 3,499.7 |
| Window p50 tick, ns | 3,148 | 3,167 | 3,185 | 3,167 |
| Window mean `overhead_ns` (tick outside the bodies), ns | 2,238.4 | 2,245.3 | 2,320.4 | 2,245.3 |

Reference, C1: the unfused chain measured 1,842.8 ns a tick and 115.2 ns per stage on this board
(`testing/board-runs/C1.md`). The probe-off figure matches it to within 2%, so the run path with
the probe off costs what C1 measured.

The probe on adds about 1.6 µs a tick to this chain, which is about 100 ns per stage. The window's
`overhead_ns` is about 140 ns a stage. Most of it is the two clock reads a step takes when a probe
is attached. There is no dev figure for probe overhead to set beside it: `docs/benchmarks-log.md`
has whole-graph `graph_overhead` figures, and they include the host's own work, not the probe's.
So the probe-on figures are recorded and not compared with dev.

## Probe cost, before and after (probe-cost, 2026-11-11)

The probe read the clock twice a step, so a 16-stage tick made 34 reads. It now reads once at the
start of the tick, once after each step that runs, and once at the end: 18 reads. A step's time runs
from the previous reading to its own end, so the runner's work between steps is counted in the next
step's body time. `overhead_ns` is therefore only the time before the first step and after the last,
and its figure before and after are not comparable.

Same board, same binary family, three runs each, medians of 101 batches of 1,000 calls:

| Row | before, run 1 / 2 / 3 | after, run 1 / 2 / 3 | median before | median after |
|---|---|---|---|---|
| One clock read (`clock_read`), ns | 45.1 / 45.1 / 46.7 | 45.9 / 45.9 / 45.9 | 45.1 | 45.9 |
| Chain, probe off, ns | 1,968.4 / 1,955.2 / 1,915.2 | 1,940.1 / 1,925.7 / 2,050.0 | 1,955.2 | 1,940.1 |
| Chain, probe on, ns | 3,550.0 / 3,573.1 / 3,557.7 | 2,881.8 / 2,889.2 / 2,883.4 | 3,557.7 | 2,883.4 |
| Probe's own cost, probe on minus off, ns | 1,594.8 / 1,617.9 / 1,642.5 | 941.7 / 963.5 / 833.4 | 1,617.9 | 941.7 |
| Window `overhead_ns`, ns (meaning changed, see above) | 2,259.3 / 2,294.6 / 2,272.8 | 112.8 / 113.3 / 112.5 | 2,272.8 | 112.8 |

The probe-on cost fell by about 42%. What is left is 18 clock reads at about 46 ns each, which is
about 830 ns a tick, and the atomic updates. Sampling (timing every Kth tick) would remove more.
It needs a flag saying which ticks were timed, so that the window never mixes timed and untimed
ticks. That is not in this change.

The probe-off path is unchanged: the budget rows (`idle_tick_16` 152 instructions, `fused_chain_16_tick`
8,778 instructions, `alloc_fused_tick` 0) are inside their limits.

## Reference: dev's tick overhead (2026-11-11)

Dev's per-stage tick overhead on the CM5, from `docs/benchmarks-log.md` (its "Fusion" section, the
CM5 measurement at `bcc9f33`): `graph_overhead` p50 fit 1,194 ns plus 655 ns per stage unfused, and
1,342 ns plus 498 ns per stage fused. These are whole-graph figures from the detector mirror, and
they are the figures C1 cites. They were not re-measured in this PR: dev's frame benches need a
separate cross-build of the frame crates. Next's probe-off chain costs 117 ns a stage (C1's
figure), so the same per-stage comparison is 5.6 times below dev's unfused overhead. As with C1,
that is recorded, not read as a speedup, because the two measure different things.

## Sampling, K = 1, 8 and 64 (probe-sampling, 2026-11-11)

The probe times every Kth tick. Every tick still counts its steps exactly, and a window reports how
many of its ticks were timed. The timing figures are over the timed ticks only. Same board, same
session, three runs each, `daedalus-cpu-timings probe_sampled 101 K`. The window holds 1,000 ticks,
so the step count is over 16,000 steps in every run.

| Row | run 1 | run 2 | run 3 | median |
|---|---|---|---|---|
| Probe off, tick, ns (same session, `probe_off`) | 1,895.7 | 1,901.7 | 1,923.1 | 1,901.7 |
| K = 1, tick, ns | 2,897.8 | 2,894.1 | 2,900.4 | 2,897.8 |
| K = 8, tick, ns | 2,065.8 | 2,060.4 | 2,065.6 | 2,065.6 |
| K = 64, tick, ns | 1,957.0 | 1,955.7 | 1,969.4 | 1,957.0 |
| K = 1, window timed ticks / steps | 1,000 / 16,000 | 1,000 / 16,000 | 1,000 / 16,000 | |
| K = 8, window timed ticks / steps | 125 / 16,000 | 125 / 16,000 | 125 / 16,000 | |
| K = 64, window timed ticks / steps | 16 / 16,000 | 16 / 16,000 | 16 / 16,000 | |
| K = 1, window mean overhead, ns | 109.1 | 109.5 | 109.6 | 109.5 |
| K = 8, window mean overhead, ns | 109.0 | 110.0 | 108.5 | 109.0 |
| K = 64, window mean overhead, ns | 106.6 | 108.8 | 108.8 | 108.8 |

Sampling takes the probe's cost from about 990 ns a tick at K = 1 to about 160 ns at K = 8 and about
55 ns at K = 64, all over the probe-off tick. The probe-off path is the same code it was: its budget
rows (`idle_tick_16`, `fused_chain_16_tick`, `alloc_fused_tick`) are inside their limits.
