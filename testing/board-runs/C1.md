# Board run: C1 serial runner

Status: partly run on CM5 2026-11-10 (per-stage and idle timings taken). Run again 2026-11-16 in the
batched session: `byte_chain` and the reference's `frame_chain`, three rounds. The reference's
unfused figure is 658 ns per stage (see the correction, 2026-11-20). No more board time for C1.

## Check

- Form: `Steps`. Plan: an unfused 16-stage chain of trivial bodies (each body copies its input
  slot to its output slot, as `core/runner/tests/support/mod.rs` `Link` does).
- Measure the per-stage cost: one tick that runs the whole chain, divided by 16, with the chain
  fed once per tick.
- Measure the idle-tick cost: a tick on the same plan with nothing fed.
- Commands: `daedalus-budget-harness chain TICKS 16 unfused` and `daedalus-budget-harness chain TICKS 1 unfused`
  (the 16-stage and the 1-stage chain, same TICKS). The per-stage time is the difference of the two
  wall times over 15 stages. `daedalus-budget-harness idle TICKS` gives the idle tick.
- Compare with `dev`, on `origin/dev`: 655 ns per stage unfused (`docs/benchmarks-log.md` there),
  27,064 instructions for an idle 16-step tick on x86.

- Next, this tree (`daedalus-cpu-timings` section `byte_chain`): a chain of 1, 4 and 16 pass-through
  CPU stages carrying one 307,200-byte value, handed on as an `Arc`, unfused and fused. Cross-build
  on NVMe: `cargo build --release --target aarch64-unknown-linux-gnu -p daedalus-cpu-timings` with
  `ZIG_TARGET=aarch64-linux-gnu.2.36`, `CARGO_TARGET_AARCH64_UNKNOWN_LINUX_GNU_LINKER` and
  `CC_aarch64_unknown_linux_gnu` set to `scripts/board/zigcc.sh`. On the board:
  `./daedalus-cpu-timings byte_chain 5000` (`bounded -c 2 900` in front to pin it to core 2; the image has no `taskset`). It prints the backing first
  (`dma-heap /dev/dma_heap/system`, or `ordinary memory` with the reason), then per-tick p50 and p99
  for each stage count, and the least-squares fit over 1, 4 and 16 stages.
- Dev, the frame chain on `origin/dev` at `bcc9f33` (the commit `docs/benchmarks-log.md` names for
  the 655 ns figure): `FRAME_CHAIN_TICKS=5000 FRAME_BENCH_CPU=2 ./frame_chain` for fused, and
  `DAEDALUS_NODE_FUSION=0 FRAME_CHAIN_TICKS=5000 FRAME_BENCH_CPU=2 ./frame_chain` for unfused. Read
  the `interface` feed table and its `graph_overhead p50 fit`. Dev's `frame_chain` takes a
  `daedalus:frame` (a 640x480 GRAY8 frame), so it is not the same work as `byte_chain`: say so
  when comparing. Its backing falls back from dma-heap to memfd to heap, and it prints which.
  Instructions come from `perf_event_open`; the column is 0 where the kernel refuses it.

## Correction, 2026-11-20 (no board time)

The 2026-11-16 section read the reference's unfused run wrong. Checked read-only in the reference at
`bcc9f33`:

- `DAEDALUS_NODE_FUSION=0` reaches `with_node_fusion(false)`. That call rebuilds the executor's compiled
  schedule with fusion off (`crates/runtime/src/executor/mod.rs:484`). So the run was unfused.
- `explain_plan` does not read that switch. It reads the plan's own fusion analysis,
  `RuntimePlan::fusion` (`crates/runtime/src/plan/explain.rs:101`). It shows which edges can fuse, so it
  prints `fused` in both runs.

So the reference's unfused figure on the CM5 is 658 ns per stage, against 498 ns fused. The fused run is
0.76 of the unfused one. The reference's own note gives x0.74 per fused stage, but that is a CM5
projection from x86 ratios ("an estimate, not a measurement", `docs/development.md` at `bcc9f33`). So
0.76 against 0.74 is a projection that comes close, not two measurements that agree.

The C1 reference steps are dropped from the batch: nothing in C1 needs the board again.
