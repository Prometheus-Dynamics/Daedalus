# Board run: E16 GPU kernel ops on V3D

Status: partly run on CM5 2026-11-10 (every kernel op matches its reference on V3D; timings not taken).

## Check

Build from NVMe, never from the HDD.

- `DAEDALUS_GPU_REQUIRED=1 cargo test -p daedalus-wgpu --test kernels -- --nocapture`. Every op
  has to match the reference there too: a mismatch on V3D is a finding, record the op and the
  first differing offset.
- Each op at 4 MiB of input, timed from `Kernels::run` to its ticket done (`Ticket::gpu_time`
  where the device writes timestamps), against the CPU kernel of the same name from
  `daedalus-kernels-sys` on the same bytes: f32 from LE, f16 to f32, f32 to unorm8, copy (the
  shader and `copy_with_engine`), hex, base64 encode, base64 decode, CRC-32. `dev` recorded
  0.005 to 0.2 ms on an RTX against 0.2 to 10 ms on its CPU. There are no CM5 figures: record
  them fresh, with which side wins for each op.
- The chain `HALF_TO_F32` then `F32_TO_UNORM8` through `merge::chain_shader` at 1 M values,
  against the two ops run one after the other.

## Result


Run on 2026-11-10 on the CM5 (raze2): OS image 2026.2.0-dev.993+e1097ec7, kernel 7.2.9-v8-16k, aarch64, 4 cores, 4 GB RAM. V3D 7.1.10.2 through the Broadcom ICD (Vulkan 1.3.354, driver 26.1.8), `/dev/dri/renderD128`. Tested commit: `next` at bdbfe947.

Method: the test binaries were built with `cargo test --release --no-run --target aarch64-unknown-linux-gnu -p <crate>` on NVMe, copied to `/tmp/daedalus-next/bin` on the board, and run as `DAEDALUS_GPU_REQUIRED=1 flock /run/lock/raze-gpu.lock ./<binary> --nocapture --test-threads=1`, with `DAEDALUS_DMA_HEAP_REQUIRED=1` where the variable is named below. Logs are on the board under `/tmp/daedalus-next/logs`.

- `wgpu-kernels` (`DAEDALUS_GPU_REQUIRED=1`): 7 of 7 pass: `a_chain_of_two_per_pixel_kernels_is_one_shader`, `copy_and_codec_kernels_match_the_references`, `copy_engine_copies_gpu_resident_bytes`, `float_kernels_match_the_references`, `gpu_base64_decode_reports_length_and_errors`, `gpu_crc32_matches_the_reference`, `two_ops_in_one_encoder_each_see_their_own_counts`. No op mismatched its reference on V3D.
- Not run: each op at 4 MiB timed from `Kernels::run` to its ticket, against the CPU kernel on the same bytes, and the `HALF_TO_F32` then `F32_TO_UNORM8` chain at 1 M values through `merge::chain_shader` against the two ops run one after the other. This branch has no harness for these timings, and there is no CM5 figure in this run. Writing one is new code, so it was not written.

## Timings, 2026-11-10

Built with `cargo build --release --target aarch64-unknown-linux-gnu -p daedalus-gpu-budgets` and run as `flock /run/lock/raze-gpu.lock ./daedalus-gpu-budgets <section>` on the CM5 (raze2): OS image 2026.2.0-dev.993+e1097ec7, kernel 7.2.9-v8-16k, V3D 7.1.10.2. Tested commit: `next` at a2ed64ea plus the timing sections of this PR. Each figure is a median of 50 runs after 5 warm-up runs, unless a line says otherwise. Three runs were made of each section, and the ranges below are the lowest and highest medians across them.

Kernel ops at 4 MiB of input, device time from submit to done (`Kernels::run` to `Ticket::wait`), with the device's own timestamp time beside it where the ticket has one. The chain of HALF_TO_F32 then F32_TO_UNORM8 over 1 M values through `merge::chain_shader`: the merged shader 8.506 to 8.548 ms, the two ops one after the other 12.953 to 12.993 ms. The merged form is 1.5 times faster.

`dev` has no CM5 figure for these, and its RTX figures (0.005 to 0.2 ms against 0.2 to 10 ms on its CPU) do not apply. On this CM5 the CPU is faster for every op but the chain. The output of every op matched its reference in the `wgpu-kernels` test (see the Result above), so this is a speed finding, not a correctness one. I have not measured why. My guess, not checked, is that the V3D compute path reads and writes storage buffers with a per-word cost, and that the four cores with NEON move these 4 MiB at close to the memory bandwidth the board has. The merged chain wins because it reads and writes memory once where the two ops read and write twice.

The 16 MiB and 1 MiB sizes the procedure names were not run here: the kernel section runs at 4 MiB as the brief asked.

## Follow-up, Copy kernel rate, 2026-11-10

Build: this branch, based on `origin/next` at 6c871a2d. CM5 kernel op at 4 MiB, submit to done, median of 50 after 5 warm-up runs. The CPU column is the same-named `daedalus-kernels-sys` function, unchanged from the earlier run.

What was wrong: the Copy shader (`copy_words`) ran one invocation per 4-byte word, so 4 MiB was about a million invocations, and each one does one scalar load and one scalar store. The same shape is in every word-per-invocation op, and those ops measure the same way on the CM5 (below), so the shape, not the op, is the common cost.

Measured on the CM5, Copy at 4 MiB with the words per invocation varied (the kernel tests pass at each):

| words per invocation | device, submit to done (3 runs, or 1 where marked) | reference: copy command |
|---|---|---|
| 1 (before) | 7.641 to 7.678 ms | 3.9 GB/s, about 1.1 ms for 4 MiB |
| 4 | 5.160 to 5.195 ms (3 runs) | |
| 8 (landed) | 4.622 to 4.653 ms (3 runs) | |
| 16 | 6.846 ms (1 run) | |

The landed shape is eight words per invocation, which is 1.65 times faster than before. Sixteen is slower, so eight is the measured best of those four.

The same size, the other word-per-invocation ops, unchanged in this PR (3 runs):

| op | device, submit to done |
|---|---|
| F32FromLe | 6.988 to 7.024 ms |
| F16ToF32 | 15.998 to 16.014 ms |
| F32ToUnorm8 | 5.451 to 5.468 ms |
| HexLower | 18.169 to 18.192 ms |

So the op is not the cost: every word-per-invocation op moves 4 MiB at about 0.6 to 0.9 GB/s on the device, and the wider invocation helps Copy only. The copy command moves the same bytes at about 3.9 GB/s, so the shader's storage access is the limit, not the number of invocations.

Not done: a vector binding (`array<vec4<u32>>`) to make each load one wide access. A WGSL binding's minimum size is one element, so a 16-byte element cannot bind the copies shorter than 16 bytes that the kernel tests check, and the chain dispatch refuses a binding below its minimum. A separate spec for copies of at least 16 bytes would need its own key in the chain cache, which is a larger change. The other ops are not widened in this PR.

Local (AMD), for comparison: Copy 0.09 ms with the eight-word shape against 0.11 ms before.

## Follow-up, kernel wide shape, 2026-11-11

Build: this branch, based on `origin/next` at ed21fa3c. CM5 kernel ops at 4 MiB, submit to done, median of 50 after 5 warm-up runs, three runs. The before figures are the landed eight-word copy and the word-per-invocation F32FromLe from the earlier table in this file.

The wide shape: a second spec for copies whose count is a whole number of vectors (16 bytes). Its binding is `array<vec4<u32>>`, so one invocation moves four words as one load and one store. The narrow spec stays for every other count. The chain cache key carries the spec index of each op. Kernels that copy bits (Copy and F32FromLe) take the wide spec; the rest do not.

| op | before (3 runs) | after (3 runs) | reference |
|---|---|---|---|
| Copy, 4 MiB | 4.622 to 4.653 ms | 2.173 to 2.219 ms | the copy command, about 1.1 ms (3.9 GB/s) |
| F32FromLe, 4 MiB | 6.988 to 7.030 ms | 2.185 to 2.234 ms | |
| F16ToF32, 4 MiB | 15.975 to 16.015 ms | unchanged | |
| F32ToUnorm8, 4 MiB | 5.451 to 5.516 ms | unchanged | |
| HexLower, 4 MiB | 18.151 to 18.192 ms | unchanged | |
| Base64Encode, 4 MiB | 15.196 to 15.218 ms | unchanged | |
| Base64Decode, 4 MiB | 90.059 to 90.077 ms | unchanged | |
| Crc32Chunks, 4 MiB | 29.089 to 30.590 ms | unchanged | |

The copy is 2.1 times faster than the narrow eight-word copy and 3.5 times faster than the one-word copy first measured here (7.64 ms). It is still about two times slower than the copy command: the wide shape gets the device to about 1.9 GB/s, not the copy command's 3.9.

Correction to the earlier notes: an intermediate figure of 1.12 ms for a vector copy was measured with the wrong thread count, so only half the output was written. It is not a result and is not recorded here; the 2.2 ms above is the vector copy with the correct count.

Found and fixed on the way: a wide copy whose count is not a whole number of vectors writes a partial vector past the end of its buffer, and the device clamps that index onto the last whole vector, which corrupts it. The wide spec is therefore only taken for counts that are whole vectors; the others use the word spec. The kernel tests cover both sides of that boundary.

Not converted in this PR: F16ToF32, F32ToUnorm8, HexLower, the base64 pair and the CRC kernel. Their figures are unchanged, and each needs its own vector body (F16ToF32 reads eight halves an invocation, F32ToUnorm8 packs four words from sixteen floats, and the base64 and CRC bodies carry state across bytes). Each is a follow-up of the same form as the copy.

## Follow-up, the rest of the kernels on the wide shape, 2026-11-11

Build: this branch, based on `origin/next` at 3b0bdccb. CM5 kernel ops at 4 MiB, submit to done, median of 50 after 5 warm-up runs, three runs each. The before figures are the landed state from the earlier tables in this file.

Shapes now in use: each op with a whole-vector count takes a vector entry point (in `kernels/wide.wgsl`, bound as `array<vec4<u32>>`, the same bindings as the Copy shape); the other counts take the word text. CRC takes word-batched loads inside its chunk (see below), with its own chunk shape unchanged.

| op | before (3 runs) | after (3 runs) | shape |
|---|---|---|---|
| F16ToF32 | 15.975 to 16.015 ms | 7.358 to 7.376 ms | eight halves an invocation, one input vector, two output vectors |
| F32ToUnorm8 | 5.451 to 5.516 ms | 2.597 to 2.610 ms | sixteen floats an invocation, four input vectors, one output vector |
| HexLower | 18.151 to 18.192 ms | 6.426 to 6.437 ms | sixteen bytes an invocation, one input vector, two output vectors |
| Crc32Chunks | 29.089 to 30.590 ms | 12.017 to 12.129 ms | word loads within the 4 KiB chunk: one load for four bytes, the same bytes in the same order |
| Base64Encode | 15.196 to 15.218 ms | 15.198 to 15.231 ms (unchanged) | a vector entry point was tried and removed, see below |
| Base64Decode | 90.059 to 90.077 ms | 90.038 to 90.077 ms (unchanged) | not converted, see below |
| Copy, F32FromLe | (earlier table) | (earlier table) | unchanged from the previous PR |

Correctness: every kernel gives its reference's bytes exactly. The kernel tests cover the counts below and above the whole-vector boundary for each op (including 1, 3, 5, 7, 15, 17, 31, 65, 4095, 4097, and 70,001 bytes of hex), and the chained paths.

Found on the way: the vector shape is only taken for whole-vector counts, because a device clamps a storage index past a buffer's end onto the last whole vector (E16 Copy follow-up). The word text stays for every other count.

Base64 encode, tried and removed: a vector entry point for 48-byte groups (three input vectors, four output vectors) measured 23.7 ms against the word text's 15.2 ms at the same count, so it was not kept. I believe the cause is the dynamic indexing into a local array of vectors (`vs[b / 16]`), which the compiler places in slow memory; a version with fixed lane indexes is the next step. The benchmark's 4 MiB count is not a multiple of 48, so the vector path would not run at 4 MiB without changing the count; the base64 comparison above is at a count of 4,194,256 bytes.

Base64 decode, not converted: the decoder checks each group of four symbols (an invalid symbol is recorded with an atomic minimum, and a padded last group is checked for stray bits), and it rereads each group's bytes for every output byte. A vector shape needs sixty-four symbols an invocation (three output vectors), so that its output words stay aligned to vectors. That body is a rewrite of the group validation, not a change of the shape alone, and it is left for its own PR. The 90 ms is the per-group work, which the vector loads would not touch on their own.

## Follow-up, base64 on the device, 2026-11-11

Build: this branch, based on `origin/next` at 5daf3ae1. CM5 kernel ops, submit to done, median of 50 after 5 warm-up runs, three runs each (`daedalus-gpu-budgets kernels`).

| op | before (3 runs) | after (3 runs) | CPU (same-named kernel) |
|---|---|---|---|
| Base64Encode, 4,194,240 bytes (the largest multiple of 48 under 4 MiB) | 15.196 to 15.218 ms, at 4,194,304 bytes | 7.279 to 7.290 ms | 2.237 to 2.240 ms |
| Base64Decode, 4 MiB of symbols | 90.059 to 90.077 ms | 25.322 to 25.376 ms | 2.250 to 2.252 ms |

Encode: a vector entry point for 48-byte groups, with fixed lane indexes in place of the dynamic index into a local array (the form that measured 23.7 ms before). Each of the 48 input bytes is a named local read from its lane, so no array is indexed by a loop variable. The generated text comes from `scripts/gen-base64-wide.py`.

Decode: a vector entry point for 64 symbols an invocation (sixteen groups, three aligned output vectors), with a status write only when an invocation finds an invalid symbol or a stray padded bit, and one atomic minimum for the invocation. The decode keeps every report the word text makes: the length, the padded last group (one or two `=`), and `InvalidSymbol { at }` at the first invalid position, including the stray bits. The status write was not the cost: a valid decode performs no atomic at all, so the 90 ms came from the per-symbol work. A one-invocation decode (64 symbols, the same host path with its status buffer) takes 0.24 ms, so the host path is not the cost either.

What is left in the 25 ms: each symbol is decoded by a select chain (`b64_value`, five selects and six comparisons), and each group carries a validity check per symbol. That is about 2,000 ALU operations an invocation, and the device spends most of the 25 ms on them. The next step is a table lookup, one load a symbol, which needs a second binding; the op's single extra slot already carries the status, so that is a change to how ops are bound, not a change to this shader. Restructuring each group into its own block, which keeps fewer values live, did not change the time (25.3 ms both ways), so register pressure is not the limit.

Correctness: the kernel tests decode and encode whole-group lengths (64, 128, 4096 and 65,536 symbols) against the CPU, with padded last groups (one and two `=`), with an invalid symbol at positions 0, 3, 4, 63, 64, 65, 127, 128 and the second-to-last symbol of each length, and with stray bits in a padded last group; each device report equals the CPU's offset. The word text remains for every other length, and its tests are unchanged.

## Follow-up, base64 and hex on tables, 2026-11-11

Build: this branch, based on `origin/next` at a7e3331b. CM5 kernel ops at 4 MiB, submit to done, median of 50 after 5 warm-up runs, three runs each (`daedalus-gpu-budgets kernels`). The before figures are the landed vector shapes from the previous table in this file.

How a table is bound: an op's extra buffers are now a list in the order its spec binds them (`encode_with` and the chained ops take `&[&Storage]`; the chained op carries its buffers in binding order), so an op can bind a status and a table, or only a table. The decode table is made once per device and bound only by the vector decode. Hex's table is made once per device and bound only by the vector hex. Each table is a small storage buffer of 256 words.

| op | before (3 runs) | after (3 runs) | what changed |
|---|---|---|---|
| Base64Decode, 4 MiB | 25.322 to 25.376 ms | 20.597 to 20.623 ms | six-bit value by a table lookup, in place of the select chain per symbol |
| HexLower, 4 MiB | 6.426 to 6.437 ms | 5.006 to 5.022 ms | the hex digits of a byte pair by a table lookup, in place of four digit formulas per word |
| Base64Encode, 4,194,240 bytes | 7.279 to 7.290 ms | 7.279 to 7.290 ms (unchanged) | a symbol table was tried and removed (below) |

Measured and rejected:
- The decode table as a `const` array in the shader (no binding at all): 1016.181 and 1019.223 ms per run, about 50 times the storage table. The compiler does not keep a 256-entry constant array in registers on V3D; it is materialised per invocation, which is what costs the time. The storage table is kept.
- The encode symbol table: 7.388 to 7.394 ms, slightly slower than the arithmetic symbol (7.279 to 7.290 ms), so the arithmetic is kept and the table removed.

The one-invocation decode (64 symbols, the same host path) is 0.215 to 0.233 ms, so the host path is still not the cost.

Desktop GPU (AMD, this machine, the same build): Base64Decode 0.174 ms, HexLower 0.069 ms, Base64Encode 0.072 ms. The narrow word decode and the earlier hex measured 0.218 ms and 0.124 ms on this machine, so the tables are not slower there. Lavapipe is not on this machine; its lane runs the same kernel tests in CI.

Correctness: the decode, the encode and the hex are checked against the CPU reference at every length the kernel tests cover, including the base64 group and chunk boundaries (invalid symbols at 0, 3, 4, 63, 64, 65, 127, 128 and the second-to-last symbol of each length; padded last groups; stray bits), and each device report equals the CPU's offset.

Remaining: the 20.6 ms decode is still 9 times the CPU's 2.3 ms. What is left is one table lookup and a few selects per symbol plus the per-symbol validity; the next step would be to read the input as bytes in larger units or to fold the validity into the table (one lookup that also yields the invalid flag), which is a later change.
