# Board run: E3 readbacks on V3D

Status: partly run on CM5 2026-11-10 (transfer tests pass; timings not taken).

## Check

Build from NVMe, never from the HDD.

- `DAEDALUS_GPU_REQUIRED=1 cargo test -p daedalus-wgpu --test transfer`: all five have to pass.
- Time, as the median of 50, a 16 MiB `wgpu.readback` step from its call to its fence resolving,
  and then the host's read of the mapped buffer. `dev` measured 13.1 ms for a 16 MiB readback
  from host-mapped memory on V3D.
- The same into a host-cached buffer made with `Storage::new_host_cached` after turning the
  dma-heap off (rename nothing: run as a user outside the `video` group). `dev` has no V3D figure
  for this, so record a fresh one.

## Result


Run on 2026-11-10 on the CM5 (raze2): OS image 2026.2.0-dev.993+e1097ec7, kernel 7.2.9-v8-16k, aarch64, 4 cores, 4 GB RAM. V3D 7.1.10.2 through the Broadcom ICD (Vulkan 1.3.354, driver 26.1.8), `/dev/dri/renderD128`. Tested commit: `next` at bdbfe947.

Logs are on the board under `/tmp/daedalus-next/logs`.

- `wgpu-transfer`: 5 of 5 pass: `bytes_go_up_come_back_and_are_counted_once_each`, `gpu_storage_reads_back_into_caller_buffers`, `integer_formats_round_trip_exactly`, `small_values_upload_too_and_buffers_are_reused`, `the_planner_is_offered_one_way_each_way`.
- Not run: the median of 50 for a 16 MiB `wgpu.readback` from its call to its fence, and the host read of the mapped buffer (dev 13.1 ms). This branch has no harness that times them; writing one is new code, so it was not written.

## Timings, 2026-11-10

Built with `cargo build --release --target aarch64-unknown-linux-gnu -p daedalus-gpu-budgets` and run as `flock /run/lock/raze-gpu.lock ./daedalus-gpu-budgets <section>` on the CM5 (raze2): OS image 2026.2.0-dev.993+e1097ec7, kernel 7.2.9-v8-16k, V3D 7.1.10.2. Tested commit: `next` at a2ed64ea plus the timing sections of this PR. Each figure is a median of 50 runs after 5 warm-up runs, unless a line says otherwise. Three runs were made of each section, and the ranges below are the lowest and highest medians across them.

Transfer steps, from the `transfers` section (`wgpu.upload`, `wgpu.upload.mapped`, `wgpu.readback`) and direct `Storage` access. The command is `daedalus-gpu-budgets transfers`.

| size | step: upload to device | step: upload to mapped | step: readback device to mapped, with the host read |
|---|---|---|---|
| 4 KiB | 0.025 to 0.033 ms | 0.001 ms | 0.054 to 0.070 ms |
| 256 KiB | 0.125 to 0.136 ms | 0.020 to 0.045 ms | 0.315 to 0.422 ms |
| 4 MiB | 2.358 to 2.499 ms | 0.794 to 0.883 ms | 4.691 to 4.959 ms |

The 16 MiB step readback that the procedure asks for: not obtained. In every run the device was lost with `Out of memory` in the first 16 MiB upload step, in the process that ran the 4 KiB to 4 MiB rows first and also when `transfers` ran alone. Whole 4 MiB steps work, so the failure starts between 4 and 16 MiB. When memory was last checked on the board (before these runs) about 1.3 GB was free. I have not found the cause; the step's staging, or the storage pool keeping blocks of that size, are the first things to check. This blocks the 16 MiB readback figure that dev measured (13.1 ms), so it stays open.

The host-cached buffer (`Storage::new_host_cached` with the dma-heap off) was not run: every run was as root, which is in the `video` group. Not run: the median of 50 for the 16 MiB step, and whether host-mapped and host-cached buffers report as mapped.

## Follow-up, 16 MiB upload and readback, 2026-11-10

Cause of the device loss: the upload step writes with `Storage::write`, which uses `queue.write_buffer`. wgpu holds each write's staging copy until the queue's next submit, and the upload steps never submit. The 4 MiB rows fit; a 16 MiB write does not fit many times over, so the device ran out of memory. Fix: `Context::note_write` counts the bytes given to the queue, and past 8 MiB (`WRITE_BUDGET`) the queue is submitted. Three CM5 runs (`budgets-up transfers`, the tool built from this branch), exit 0 in every run:

| case | run 1 | run 2 | run 3 | dev figure |
|---|---|---|---|---|
| 16 MiB step upload to device | 19.573 ms | 19.170 ms | 18.983 ms | not quoted |
| 16 MiB step upload to mapped | 3.536 ms | 3.463 ms | 3.480 ms | not quoted |
| 16 MiB step readback device to mapped, with the host read | 17.518 ms | 18.488 ms | 17.829 ms | 13.1 ms for a readback from host-mapped memory |
| 16 MiB host read of the mapped buffer (direct) | 12.271 ms | 13.153 ms | 12.422 ms | 13.1 ms |

Reading the rows: the step-plus-read figure is 17.5 to 18.5 ms against dev's 13.1 ms, so it misses by about a third. The host read on its own is 12.3 to 13.2 ms, which meets dev's figure. The procedure's wording puts the host read inside the step figure, so the step row is the one to compare, and it misses. Not checked: whether dev's 13.1 ms included the host read.

## Follow-up, readback into dma-heap memory, 2026-11-10

Build: this branch, based on `origin/next` at 3399ba00. Three CM5 runs of `daedalus-gpu-budgets transfers`, each row a median of 50 after 5 warm-up runs, and the example GPU test binary run on the board under `flock /run/lock/raze-gpu.lock`.

The readback step now has two routes. `wgpu.readback` copies into host-mapped memory and `wgpu.readback.heap` copies into dma-heap memory. The heap route is offered only by an open device that imports dma-bufs, and the planner prefers it by cost.

| case | run 1 | run 2 | run 3 | dev figure |
|---|---|---|---|---|
| 16 MiB step readback to dma-heap, with the host read | 12.175 ms | 12.122 ms | 12.285 ms | 13.1 ms |
| 16 MiB step readback to host-mapped, with the host read (for comparison) | 17.174 ms | 16.834 ms | 17.709 ms | 13.1 ms |
| 4 MiB step readback to dma-heap, with the host read | 3.718 ms | 3.838 ms | 3.607 ms | not quoted |

The heap route meets dev's 13.1 ms and the host-mapped route misses it. The earlier measurement in this file (8.9 ms together, device copy 4.15 ms plus host read 4.77 ms) was a direct probe without the step; the step row above is the figure to compare.

The example GPU test `the_readback_takes_the_route_the_device_can_run` passed on the CM5 and checks that a graph reading back plans to `wgpu.readback.heap` then `wgpu.map.dmaheap`. Three of the example's tests (`fragment_matches_cpu`, `mixed_round_trip_matches_cpu`, `upload_download_round_trip`) run example binaries from their build-tree paths, which do not exist on the board, so they cannot run there. They pass on the desktop GPU.

## Timings, 2026-11-11

Build: this branch, based on `origin/next` at 9039013d. Three CM5 runs (OS image 2026.2.0-dev.993+e1097ec7, V3D 7.1.10.2), `daedalus-gpu-budgets pixels busy cached heap-read` under `flock /run/lock/raze-gpu.lock`. Each figure is a median of 50 after 5 warm-up runs, and the ranges are the lowest and highest of the three runs.

The host-cached buffer at 16 MiB, `Storage::new_host_cached`. On this board the device has no host-cached memory, so the buffer is a dma-heap buffer: the space name is `wgpu.dmaheap`, which the run prints.

- Host write, 16 MiB: 3.712 to 3.787 ms.
- Host read, 16 MiB: 4.376 to 4.713 ms.

No dev figure is quoted for the host-cached buffer on V3D (E3 records that dev had none), so this is the fresh figure the procedure asked for.

The 16 MiB dma-heap read, which dev quotes at 3.6 ms (E17). Command: `daedalus-gpu-budgets heap-read`, three runs.

- `Storage::read_into`, the storage's own read: 4.099 to 4.647 ms.
- Raw dma-heap read of the same kind of memory, with no device buffer on it: 3.408 ms.
- Raw read after the device buffer is dropped: 3.927 ms.
- A sync pair (`begin_cpu_access` and `end_cpu_access`) on its own: 0.001 ms. A sync, copy and sync: 3.328 to 3.490 ms.

Where the time goes: the sync is free, and the time is the copy out of the mapping at about 4 to 5 GB/s. The storage's read calls the same begin, copy and end sequence, so the storage path adds no structure of its own. The gap between the storage's read and the raw read (about 0.5 to 0.9 ms) is inside the run-to-run spread of the raw figure (3.3 to 3.9 ms). So the figure that is measured in the same way as dev's 3.6 ms is the raw copy, at 3.3 to 3.9 ms, which meets it; the storage read is 0.5 to 0.9 ms over it and misses by about 15 percent. I did not find a change in the storage path that removes that gap; the copy is bound by the memory bandwidth of the mapping.
