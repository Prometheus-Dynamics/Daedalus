# Board run: E3 readbacks on V3D

Status: partly run on CM5 2026-11-10 (transfer tests pass; timings not taken).

## Check

Build from NVMe, never from the HDD.

- `DAEDALUS_GPU_REQUIRED=1 cargo test -p daedalus-wgpu --test transfer`: all five have to pass.
- Time, as the median of 50, a 16 MiB `wgpu.readback` step from its call to its fence resolving,
  and then the host's read of the mapped buffer. `dev` measured 13.1 ms for a 16 MiB readback
  from host-mapped memory on V3D.
- The same into a host-cached buffer made with `Storage::new_host_cached` after turning the
  dma-heap off (rename nothing: run as a user outside the `video` group). `dev` has no V3D figure
  for this, so record a fresh one.

## Result


Run on 2026-11-10 on the CM5 (raze2): OS image 2026.2.0-dev.993+e1097ec7, kernel 7.2.9-v8-16k, aarch64, 4 cores, 4 GB RAM. V3D 7.1.10.2 through the Broadcom ICD (Vulkan 1.3.354, driver 26.1.8), `/dev/dri/renderD128`. Tested commit: `next` at bdbfe947.

Method: the test binaries were built with `cargo test --release --no-run --target aarch64-unknown-linux-gnu -p <crate>` on NVMe, copied to `/tmp/daedalus-next/bin` on the board, and run as `DAEDALUS_GPU_REQUIRED=1 flock /run/lock/raze-gpu.lock ./<binary> --nocapture --test-threads=1`, with `DAEDALUS_DMA_HEAP_REQUIRED=1` where the variable is named below. Logs are on the board under `/tmp/daedalus-next/logs`.

- `wgpu-transfer`: 5 of 5 pass: `bytes_go_up_come_back_and_are_counted_once_each`, `gpu_storage_reads_back_into_caller_buffers`, `integer_formats_round_trip_exactly`, `small_values_upload_too_and_buffers_are_reused`, `the_planner_is_offered_one_way_each_way`.
- Not run: the median of 50 for a 16 MiB `wgpu.readback` from its call to its fence, and the host read of the mapped buffer (dev 13.1 ms). This branch has no harness that times them; writing one is new code, so it was not written.
- Not run: the host-cached buffer from `Storage::new_host_cached` with the dma-heap off. That needs a user outside the `video` group; every run here was as root, so it was not done.
- Related figures from `daedalus-gpu-budgets readback` (a different measure from E3's 16 MiB step, so not compared with dev's 13.1 ms): 4 KiB read back 0.061 ms; 256 KiB 0.262 ms; 4096 KiB 3.450 ms; 64 KiB upload and back, 1 upload and 1 download.

## Timings, 2026-11-10

Built with `cargo build --release --target aarch64-unknown-linux-gnu -p daedalus-gpu-budgets` and run as `flock /run/lock/raze-gpu.lock ./daedalus-gpu-budgets <section>` on the CM5 (raze2): OS image 2026.2.0-dev.993+e1097ec7, kernel 7.2.9-v8-16k, V3D 7.1.10.2. Tested commit: `next` at a2ed64ea plus the timing sections of this PR. Each figure is a median of 50 runs after 5 warm-up runs, unless a line says otherwise. Three runs were made of each section, and the ranges below are the lowest and highest medians across them.

Transfer steps, from the `transfers` section (`wgpu.upload`, `wgpu.upload.mapped`, `wgpu.readback`) and direct `Storage` access. The command is `daedalus-gpu-budgets transfers`.

| size | step: upload to device | step: upload to mapped | step: readback device to mapped, with the host read |
|---|---|---|---|
| 4 KiB | 0.025 to 0.033 ms | 0.001 ms | 0.054 to 0.070 ms |
| 256 KiB | 0.125 to 0.136 ms | 0.020 to 0.045 ms | 0.315 to 0.422 ms |
| 4 MiB | 2.358 to 2.499 ms | 0.794 to 0.883 ms | 4.691 to 4.959 ms |

The 16 MiB step readback that the procedure asks for: not obtained. In every run the device was lost with `Out of memory` in the first 16 MiB upload step, in the process that ran the 4 KiB to 4 MiB rows first and also when `transfers` ran alone. Whole 4 MiB steps work, so the failure starts between 4 and 16 MiB. When memory was last checked on the board (before these runs) about 1.3 GB was free. I have not found the cause; the step's staging, or the storage pool keeping blocks of that size, are the first things to check. This blocks the 16 MiB readback figure that dev measured (13.1 ms), so it stays open.

The host-cached buffer (`Storage::new_host_cached` with the dma-heap off) was not run: every run was as root, which is in the `video` group. Not run: the median of 50 for the 16 MiB step, and whether host-mapped and host-cached buffers report as mapped.
